# 對戰時間都花在哪（2026-08-05 雙邊實測）

「戰鬥太久，能不能加速？」這題每隔一陣子就會被重新提一次。這份文件的目的是
讓它**只需要被回答一次**。

結論先講：**客戶端幾乎沒有槓桿。** 一場對戰約 385 秒，其中

| 去處                                 | 秒數      | 誰控制         |
| ------------------------------------ | --------- | -------------- |
| 伺服器排程（兩則事件之間的固定間隔） | ~230s     | 伺服器，動不了 |
| 玩家思考（雙方決策窗合併）           | ~187s     | 玩家自己       |
| **動畫（真正擋住玩家的那部分）**     | **11.3s** | 我們           |

加速動畫的**理論上界是 11.3 秒**。×3 實際省 7.5 秒（2%）。倍率再高也不會超過
11.3 秒 —— 那是決策窗裡全部的動畫時間。

擷取方式：`companion watch --port 9333` + `--port 1221` 同時錄，
加上一支只數 tween 的動畫探針。**兩邊一定要同時錄**，理由見下面。

---

## 為什麼一定要雙邊錄

`I_am_ok` 只送不收（[battle-events.md](battle-events.md)），所以單邊 log 只知道
**自己**什麼時候按 OK，不知道對手。而移動階段是**雙方都按才結束**，階段長度是
`max(A, B)` 不是 A。

> ⚠ **2026-08-06 更正：`max(A,B)` 只適用於移動階段。** 攻擊與防禦階段是
> **循序**的 —— 你送出 `I_am_ok` 之後 41~44ms 就收到 `cardController2X`，
> 自己那半段立刻結束，完全不等對手（15 次樣本）。
> 下面的「決策合計」仍然是雙邊的合併值，這條更正不影響本文件的數字，
> 但它改變了**該怎麼縮短它**：攻防階段單邊就能省，不必等對手也裝插件。
> 見 [battle-preplay.md](battle-preplay.md)。

實測差距：同一場對戰，單邊算出「非玩家時間 81.1%」，雙邊算出 **67.9%**。
單邊會把對手的思考時間整包算進「非玩家時間」，然後你就會去優化一個不存在的東西。

兩份 log 各自從自己的第一則事件起算 t=0，用共同的廣播事件
（`movepower` / `distance` / `diceRoll`）取時間差中位數對齊。實測 52~64 個樣本
一致率 100%。

---

## 伺服器不等客戶端 —— 這條有受控實驗

一開始只能觀察到「`I_am_ok` 送出後到下次可操作的 7.86 秒裡，客戶端一則都沒送
出去，全是 `←收到`」。那只證明客戶端沒說話，不能排除伺服器在等別的東西
（例如傳輸層 ACK）。

後來裝上 `companion speed`（tween ×3）意外做成了一個受控實驗：**客戶端跑快
三倍，伺服器的間隔紋風不動。**

```
                      加速前     加速後
diceRoll → chara_A     7.48s  →   7.42s
atkvalue → diceRoll    2.01s  →   2.00s
```

所以那些間隔是**伺服器自己的計時器**，跟客戶端演多快完全無關。

### 已證實的固定間隔（全距 ≤0.02s）

| 銜接                          | 間隔  | 樣本 |
| ----------------------------- | ----- | ---- |
| `atkvalue → diceRoll`         | 2.01s | 8~9  |
| `atkvalue → chara_B`          | 2.00s | 4    |
| `initiativeX → movepower`     | 2.00s | 6    |
| `cardOpen_B → movepower`      | 1.97s | 7    |
| `dmgToX → chara_X`            | 1.40s | 7    |
| `endMovePhase → phaselabel_X` | 1.31s | 7    |
| `goToBochi → endMovePhase`    | 1.00s | 7    |
| `eventCard → endDrawPhase`    | 0.50s | 4    |

最貴的是 `diceRoll → chara_X`：**約 7.5 秒 × 每場 7 到 8 次 ≈ 55 秒**，
而其中客戶端只演了約 1.0 秒。其餘 6.4 秒畫面是不動的。

> 這也解釋了 CheatEngine 為什麼「一加速就斷線，而且沒變快」——
> 它壓縮的是同一段動畫，剩下的呆等它一樣動不了。斷線機制見下面。

---

## 動畫的上界：11.3 秒

動畫探針（頁面端每 100ms 數一次非無限循環的 tween），對齊到事件時間軸之後：

```
決策窗          17 個，合計 152.7s
  其中在演動畫  11.3s   (7%)      ← 只有這段是「想動但被動畫擋著」
整場動畫總量    58.2s
  躲在伺服器空檔裡  46.9s          ← 省了也沒用，伺服器照樣等
```

**只有落在決策窗裡的動畫才值得加速。** 躲在伺服器空檔裡的那 46.9 秒，演得再快
也只是提早開始盯著不動的畫面。

實測 ×3 之後，同一個決策窗裡連續兩個動作的間隔中位數 **0.40s → 0.23s**，
但最快值 0.16s 完全沒變 —— 那是人的點擊速度與網路 RTT，不是動畫。

---

## ⚠ 量這件事踩過的三個坑

三個都會給出**看起來很合理但錯很多**的數字。前兩個讓「動畫的上界」一度被算成
75 秒、「加速效果」一度被算成 −50%。

### 1. 不能用「玩家操作前最後一次有動畫的時刻」當阻塞時間

直覺的做法是：`okVisibleX` 到達 → 找玩家第一個動作之前最後一個「在演動畫」的
取樣 → 兩者之差就是被擋住的時間。

**但玩家想 20 秒的窗會被算成阻塞 20 秒** —— 期間任何一次無關的 tween（例如
顯示對手的動作）都會把終點往後推。這個錯讓上界從 7.5 秒膨脹成 75 秒。

正確做法是直接積分「決策窗 ∩ 動畫忙碌」的時間。

### 2. 一份 log 可能含**兩場**對戰

`watch` 開著不動，玩家打完會再開一場。數回合數時如果 grep 整個檔案、時長卻只
取第一場，分子含兩場、分母只有一場，會得到假的「每回合快一半」。

計數一定要限制在同一段戰鬥區間內（首次 `drawPhase` → `leaveRoom`）。

### 3. 倒數速率不能只在「數值下降時」取樣

TIME 顯示在 10 秒以上是整數。如果只在 `v < prev` 時記錄速率，不管真實速率是
多少，量到的永遠是「1 格 ÷ 一個取樣間隔」。實測 232 筆樣本全部是 1.99，
而真實速率是 1.00。

兩個正確做法：整段線性回歸（含持平樣本），或**直接讀 `scene.timelimit`**
（浮點、0.1 解析度、遊戲自己維護的那個變數）。後者最乾淨：

```
AttackPhaseA  27.5 → 25.5  2.00s = 1.00 格/真實秒  paused=false  tweens×3 time×1
```

## 斷線：心跳 10 秒，錯過一次就自己關 socket

`main.js` 的 `WSClient`：

```js
static DEFAULT_HEARTBEAT = 10;                 // 秒
setInterval(() => {
  if (!alive) { socket.close(); return; }      // 上一輪的 __pong_c 沒回來
  alive = false; emit("__ping_c", Date.now());
}, heartbeat * 1000);
```

CheatEngine 那種 process 級加速會 hook `QueryPerformanceCounter`，Chromium 的
`setInterval` 走的就是那條，於是這個 window 被壓縮 k 倍而伺服器的 pong 照真實
速度回來 —— **必斷**。不是「戰鬥時才有檢測」，是全程都有。

**心跳是純 `setInterval`，活在 Phaser 外面**，所以 Phaser 的 timeScale
結構上碰不到它。這是 `patch-speed.ts` 安全的根據，不是「小心一點就不會斷」。

⚠ 2026-08-05 實測時網頁版斷過一次（**沒有**開任何加速）：6 條 socket 在 20ms
內同時重連。單一遊戲邏輯問題不會讓六條一起掉 —— 那是 VPN 抖動撞到 10 秒心跳。
雙開需要 VPN（見 [launching.md](launching.md)），所以那台天生比較脆弱。

## 已實作：`companion speed`

```
companion speed [--port N] [--factor N]      # 預設 ×3，上限 10
```

動 `scene.tweens.timeScale`、`game.anims.globalTimeScale`，以及**只有 MainA
那一顆** `scene.time.timeScale`。實作在
[`patch-speed.ts`](../packages/cdp-adapter/src/patch-speed.ts)，三條硬約束：

### ⚠ 絕對不能動**階段場景**的 `scene.time.timeScale`

> **2026-08-06 修訂。** 這一節原本寫「`scene.time` 一律不碰」。後來確認
> `MainA.time` 與階段場景的 `.time` 是**不同的 Clock 物件**，而亮牌
> （`CardOpen.showcards` 的 `delay: 200`）與出牌後的 `await 110ms` 都掛在
> MainA 那顆。加速 MainA 的 Clock 在結構上碰不到倒數，所以現在會動它 ——
> 用場景鍵白名單 `REVEAL_CLOCK_SCENES`，名單外一律不碰。
> 理由與佐證見 [battle-preplay.md](battle-preplay.md)「兩顆 Clock」。
>
> 底下這一段講的是**階段場景那一顆**，它的禁令完全沒有放寬。

倒數計時器是 `scene.time` 裡的 `TimerEvent`（171.js）：

```js
timer_reset() {
  this.timelimit = 30;
  this.timer.reset({ delay: 100, callback: () => { this.timelimit -= 0.1; … } });
}
```

加速它有兩個後果，第二個更嚴重：

1. 玩家看到假的剩餘秒數
2. **WP-12 仲裁讀那個 TIME 算硬底線**（[battle-events.md](battle-events.md)
   「讀 TIME 顯示」那節），倒數跑快 N 倍 → 硬底線提早 N 倍觸發 → `I_am_ok`
   被提早送出

兩個功能各自都對，合起來會害玩家在移動階段被強制提早承諾 —— 正是 WP-12
存在目的的反面。

### ⚠ 無限循環的 tween 要補償回原速

玩家實測回報「讀秒會提早變紅」。倒數的警示條就是一條循環 tween：

```js
this.limit10Tween = this.tweens.add({
  targets: this.time_base2,
  alpha: 1,
  repeat: -1,
  duration: 500,
  yoyo: true,
  delay: 2e4, // 20 秒後開始閃 ＝ 剩 10 秒
});
```

`delay: 20000` 被 ×3 壓成 6.7 真實秒，於是紅色警告在**還剩 23 秒**時就亮起來
—— 數字是對的，條卻在騙人，而且是往「更慌」的方向。

補償方式是設該 tween 自己的 `timeScale = 1/factor`（有效速率 = manager × tween）。

⚠ **判斷要用 `repeat === -1`，不要寫死 `limit10Tween` 這個名字** ——
那個屬性名在正式 bundle 裡被改掉了，讀不到。用通則還有一個好處：循環 tween
都是待機動畫、狀態指示、警示閃爍這類**語意上跟時間有關**的東西，本來就不該
被當成「演出」加速。

### 骰子不吃 Phaser 的 timeScale

擲骰是 three.js + cannon 的 3D 物理骰（807.js 的 `DiceD6AttackA` 那組），
收斂判定是「連續 50 個 `postStep` 都靜止」—— 是**步數**不是時間。
但它只值約 1 秒／次，不值得為它多開一條路。

## 真正的槓桿在「階段上限」，不在動畫

玩家提的方向（2026-08-05）：

> OK 鈕換成「準備」，偏好設定裡填期望的準備時間（15 秒、10 秒之類）。
> 時間一到，**由中間伺服器（ulgg）發鎖定訊號，讓兩邊的插件同時鎖定** ——
> 即使遊戲伺服器給的是 31 秒。

這跟 WP-12 的[不變量 2](battle-features.md) 相容：ulgg 發的是**合成訊號**
（「時間到了，兩邊一起鎖」），不是單獨告訴任何一方對手的狀態。所以
「伺服器從不下發對手 OK 狀態」那條 fairplay 性質仍然保住。

不變量 1 也照舊：**本機硬底線優先**。鎖定訊號沒送到（ulgg 掛了、網路斷了）
時，本機仍然要在 `okInvisibleX` 之前送出 `I_am_ok`，否則就是棄權。ulgg 是
加速器，不是唯一出口。

用實際分布算過，這個方向比加速大一個數量級，**但它是保險，不是穩定收益**。

### 第一場（384.6s，28 個階段，決策合計 187.1s）

```
中位 3.6s   75% 6.1s   90% 28.8s   最長 31.0s

上限   受影響階段   省下     佔全場
 25s     3/28        15.6s    4.1%
 20s     3/28        30.6s    8.0%
 15s     3/28        45.6s   11.9%
 10s     5/28        66.6s   17.3%
```

**28 個階段裡只有 3 個超過 15 秒，但那 3 個就佔了 45.6 秒。** 長尾主導。
最長的剛好 31.0 秒 —— 那是伺服器的硬上限，代表那幾個階段是**跑到逾時**的。

### 第二場（361.0s，38 個階段，決策合計 97.8s）

```
中位 2.3s   75% 3.3s   90% 5.1s   最長 8.7s

任何上限（25/20/15/12/10s）都省不到任何時間。
```

**一秒都省不到。** 沒有任何階段超過 8.7 秒。

### 所以

| 手段          | 好的情況 | 壞的情況 |
| ------------- | -------- | -------- |
| 動畫加速 ×3   | 7.5s     | 7.5s     |
| 15 秒階段上限 | 45.6s    | **0s**   |

階段上限的期望值比加速高，但**變異數極大**：它治的是「偶爾有人卡很久」，
而不是「每一場都比較快」。兩場之間光是玩家決策速度的差異（187.1s vs 97.8s，
而且第二場階段數還更多）就比這兩個手段加起來還大。

⚠ 三件事要一起講清楚，否則文案會誤導：

1. **這是插件自己的邏輯，不是改遊戲。** 伺服器仍然是 31 秒硬砍
   （[battle-features.md](battle-features.md)），插件只能更早送出 `I_am_ok`，
   不可能延長。文案不要讓玩家以為插件改得動伺服器判定。
2. **只在對手也有插件時有意義。** 單方面縮短只是讓自己更早承諾 ——
   那正是「先按 OK 的人被懲罰」的不對稱，也是 WP-12 要消除的東西。
3. **不要把它包裝成抓拖條仔。** 那 3 個長階段可能是關鍵局面的深思。
   [battle-features.md](battle-features.md) 對規則 0 的評論同樣適用。

### ⬜ 沒解的設計題：雙方偏好不同時，聽誰的？

偏好設定是個人的，但鎖定訊號是**雙方共用**的，所以一定要有一個裁決規則。
三個選項都有問題，而且問題的方向不一樣：

| 規則                             | 後果                                                                           |
| -------------------------------- | ------------------------------------------------------------------------------ |
| 取較短的                         | 我填 5 秒就能**單方面**把對手的思考時間砍到 5 秒 —— 把不對稱換了個方向重新引入 |
| 取較長的                         | 對手填 31 秒等於退回現狀，這個功能被單方面關掉                                 |
| 握手時協商，談不攏就退回單邊模式 | 跟規則版本不相容的處理一致，但「談不攏」會很常見                               |

⚠ **不能默默選一個。** 這條決定的是「對手能不能逼我快點出牌」，而那是勝負
問題不是顯示問題。建議跟規則版本走同一套：**握手時交換偏好，不相容就雙方
都退回單邊模式**（[battle-features.md](battle-features.md)「規則版本」那節），
因為單邊模式本來就是安全的預設。

另一個相關的：**準備時間應該從哪一刻起算？** `okVisibleX` 到達的時刻在兩個
客戶端不完全同步（網路延遲），而且凍結（`timerPause`）期間該不該計時也要決定
—— 遊戲自己的倒數在凍結時是停的。用 ulgg 的單一時鐘發訊號可以繞過前者，
但後者仍然要選。

## 給下一個問「能不能加速」的人

- 動畫加速已經做了，上限 7.5 秒／場。**不會再更多**，換倍率也一樣。
- 伺服器排程約 230 秒，**沒有任何客戶端手段**能碰到它。已經用受控實驗證實。
- 想再縮短就只剩「雙方約定的階段上限」，而它是保險性質的，期望值高但不保證。
- 玩家自己的決策速度比上面全部加起來都大。

⚠ **最後一句在 2026-08-06 被推翻了一半。** 決策速度確實不可工程化，但
**決策的「時機」可以** —— 每個階段解鎖前都有 1.5~3.7 秒的死時間，資訊早就到齊
而玩家還不能動。把決策搬進那段死時間（預先出牌）估計單邊約 23 秒／場、
雙邊約 45 秒，是目前找到最大的槓桿。

而且它跟本文件的另一個結論相容：預先出牌**不會**碰伺服器排程那 230 秒，
它搶的是決策時間那 187.1s / 97.8s。細節與實測見
[battle-preplay.md](battle-preplay.md)。
