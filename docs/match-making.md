# 自動配對與跨版本相容（WP-16）

「兩個約定同一套 COST 規則的人，自動湊成一場有密碼的自訂房。」

這份文件回答三個問題：

1. 為什麼配對需要中間人 —— 遊戲自己的佇列做不到這件事
2. 為什麼「規則 hash 一樣」**不能**當成配對的條件
3. 那要拿什麼當條件，以及那樣還安不安全

---

## 1. 為什麼要有中間人

遊戲自己有快速比賽，但實測 `on_server_status` 之後就知道它用不上：

```
channels = { "1": { type: "ranked", cost: [57,66,78] },   ← 亞歷山卓城
             "2": { type: "duel" } }                       ← 迪特赫姆
```

`quick_wait` 是**伺服器端**的佇列，只有 ranked 頻道有，而且 COST 階層是伺服器
定的（用**原版 COST** 判）。自訂規則的約戰只能發生在 duel 頻道，那裡沒有佇列。

所以在有中間人之前，「約戰」只能是：開一間房、把房號與密碼用 Discord 傳給對手。
那是**認識的兩個人**才能做的事，而自訂 COST 規則要成為一個環境，需要陌生人也
配得到彼此。

中間人（`apps/link-worker`）因此多了第二條路徑：

| 路徑                 | 什麼時候連                       | 一個實例是什麼              |
| -------------------- | -------------------------------- | --------------------------- |
| `wss://…/r/<房號>`   | 對戰中                           | 一間對戰房（側通道，WP-15） |
| `wss://…/q/<配對鍵>` | **玩家按下「開始自動配對」之後** | 一條配對佇列                |

兩條走同一台伺服器、同一套訊息大小與流量限制，玩家的設定裡只有一格。

## 2. 為什麼配對鍵不能是規則的 hash

第一版的配對鍵是這樣算的：

```
matchKey = sha256(contentHash | 頻道 | 3vs3 | COST 上限)
```

`contentHash` 是整份規則內容的 SHA-256。這個設計有一個很漂亮的性質：
**規則不一樣的人算出不同的鍵，落在不同的 Durable Object，物理上碰不到對方** ——
不需要任何一方自律，也不需要中間人比對什麼。

它的問題是把「版本相同」當成了「可以一起打」的必要條件，而那不成立：

```
版本 A                     版本 B
  R3 利恩   = 22             R3 利恩   = 22
  R3 艾伯   = 18             R3 艾伯   = 18
  R3 阿貝爾 = 17             R3 阿貝爾 = 17
  新角色 X  = 25             新角色 X  = 26   ← 只差這一個
```

雙方都帶利恩＋艾伯＋阿貝爾出戰。兩邊算出來的每一個數字都一樣，
**「X 是 25 還是 26」對這一場沒有任何可觀測的影響** —— 但整表 hash 不同，
於是他們永遠配不到對方。

規則作者每發一次版就把社群切成兩半，而切開的理由是一個沒有人帶上場的角色。
這叫版本碎片化，不是公平性。

### 真正要問的問題

不是「兩份規則是不是同一份」，而是

```
Eval(這一場的牌組, 規則 A) == Eval(這一場的牌組, 規則 B)
```

也就是**局部語義等價**。所以身分拆成三層，而**只有第三層是配對的閘門**：

| 層                   | 是什麼                           | 用途                 | 在哪               |
| -------------------- | -------------------------------- | -------------------- | ------------------ |
| `contentHash`        | 整份規則的 SHA-256               | 版本識別、統計、稽核 | `@ulr/rule-schema` |
| 配對鍵               | `ruleSetId` + 頻道 + 3vs3 + 上限 | 決定排在哪一條佇列   | `matchKey()`       |
| **`evaluationHash`** | **這一場的完整計算結果**         | **這一場能不能成立** | `@ulr/cost-engine` |

配對鍵裡放的是 `ruleSetId`（`publisherSlug/ruleSlug`），所以**同一套規則的不同
版本會排在同一條佇列**，不同規則（燈皇 vs 亞城）仍然物理上碰不到。

## 3. 語義指紋蓋的是整份計算結果，不是總和

只比總和會出事：

```
規則 A：20 + 20 + 20，壓 C −2  → 58
規則 B：19 + 20 + 19，壓 C  0  → 58
```

總和一樣，單角 COST 完全不同。之後任何看單角數字的限制或畫面都會產生歧義。

所以指紋蓋的是逐角定價、逐對壓 C、未定價清單、規則宣告的上限、總和：

```jsonc
{
  "v": 1,
  "characters": [
    ["abel_r3", "17.00"],
    ["evarist_r3", "18.00"],
    ["leon_r3", "22.00"],
  ],
  "compression": [["abel_r3", "leon_r3", "5.00", "5.00"]],
  "unknown": [],
  "limit": "62.00",
  "total": "62.00",
}
```

正規化之後取 SHA-256 —— **跟規則的 contentHash 是同一套 RFC 8785 (JCS)**，
所以 ULGG 那邊（PHP）照 [canonical-json.md](canonical-json.md) 實作就對得上。

三件事值得單獨講：

- **角色鍵會排序。** 槽位順序是玩家在牌組畫面上排的，它不影響任何計算
  （壓 C 是每一對各判一次），卻會讓指紋不同。
- **數值是固定兩位小數的字串**，不是數字。浮點的尾巴會讓兩台電腦算出不同的
  字串（`8.8 + 26.6 + 26.6` 是 `62.00000000000001`）。
- **`teamCostLimit` 與壓 C 區間也在裡面。** 兩份規則只差在上限也是真的差異：
  同一副牌在一邊合法、另一邊超標，那不是同一場比賽。

### ⚠ 要算四次，不是兩次

「甲用 A 算自己 = 57，乙用 B 算自己 = 57」證明不了什麼。要成立的是交叉的四次：

```
Eval(A, 甲牌) == Eval(B, 甲牌)   且   Eval(A, 乙牌) == Eval(B, 乙牌)
```

只驗自己那副的話會發生這種事：

```
甲的牌   規則 A → 60    規則 B → 61
乙的牌   規則 A → 59    規則 B → 60
```

兩人各自看到的數字都「合理」，但他們身處不同的規則宇宙 —— 同一場比賽裡，
對手的隊伍在我眼中是 60、在他眼中是 61。

## 4. 完整流程

```
  host                        佇列                        guest
   │── q-hello(鍵, 規則標籤) ──▶│◀──────────── q-hello ─────│
   │◀── q-matched(角色, token, 對手標籤) ── q-matched ─────▶│
   │                           │                           │
   │  標籤一樣 → EXACT，跳到開房（牌組完全不交換）           │
   │                           │                           │
   │── q-deck(我的描述子) ─────▶│◀──────── q-deck ──────────│
   │◀── q-deck(對手的) ────────│──────── q-deck ──────────▶│
   │  各自用**自己那份規則**算兩副牌 → 兩個指紋              │
   │── q-eval(host指紋, guest指紋) ▶│◀────── q-eval ────────│
   │  四個指紋兩兩相等 → COMPATIBLE，否則 INCOMPATIBLE      │
   │                           │                           │
  建房(pass=token)             │                           │
   │── q-room(roomId) ────────▶│──────── q-room ──────────▶│
   │                           │                    進房(roomId, token)
```

`token` 同時是**房間密碼**（遊戲自己的密碼就是 8 碼英數，格式一致），所以外人
看得到那間房卻進不去。⚠ **房名絕對不能包含 token** —— 房名是公開的。

三態的結果：

| 判決           | 意思                                              |
| -------------- | ------------------------------------------------- |
| `EXACT`        | 兩邊的 `contentHash` 就是同一個。不必交換任何東西 |
| `COMPATIBLE`   | 規則不同，但這一場的四次計算完全一致              |
| `INCOMPATIBLE` | 至少有一副牌在兩份規則下算出不同的東西            |

### ⚠ 中間人必須是**部署過佇列**的那一版

`/r/<房號>`（側通道）與 `/q/<配對鍵>`（佇列）是同一台 Worker 的兩條路由，但
**它們是分開上線的** —— 側通道早就在跑，佇列是 WP-16 才加的。所以會出現這種
狀態：房間側通道一切正常、自動配對卻永遠配不到，因為 `/q/` 回 404。

```powershell
# 這一條就是在問「那台有沒有佇列」
curl.exe -i https://ulr-link.lldavuull.workers.dev/q/0123456789abcdef
#   426 expected websocket → 有（正常，因為 curl 沒帶 Upgrade）
#   404 not found          → 沒有，要重新部署
npm --workspace apps/link-worker run deploy
```

2026-08-16 實測就是這個：兩個客戶端條件完全相同（頻道 2、同一份 shinon 規則、
上限 57），畫面兩邊都寫「排隊中 · 只有你」，而那台 Worker 還是沒有佇列的舊版。

> ⚠ 插件那邊的症狀**完全沉默**是另一個 bug，已經修掉：`phase` 在按下按鈕的
> 當下就被設成 `queued`，而 WebSocket 那時才剛開始連。現在 `PairingStatus.linked`
> 只有在收到 `q-welcome` 之後才是 true，畫面會分開講「還沒連上中間人」與
> 「排隊中，只有你」，記錄檔也會印連不上的那幾行。

### 排隊不是輪詢 —— 但重連是

配對**沒有任何輪詢**。連上去是一個請求，之後那條 WebSocket 就一直開著，
中間人主動推 `q-matched` / `q-deck` / `q-room` 過來；插件也沒有心跳。
一場配對從頭到尾對雲端來說就是**一個請求**，之後的訊息走 Durable Object
（而且進 hibernation，閒置不計時間）。

會產生流量的是**連不上時的重試** —— 那不是在問「配對好了沒」，是在試著把
訂閱建立起來，而一台回 404 的伺服器你沒辦法向它訂閱任何東西。

| 版本                  | 卡住一天的請求數 |
| --------------------- | ---------------- |
| 固定 2 秒重試（原本） | 43,200           |
| 指數退避，上限 60 秒  | 1,440            |

2026-08-16 就是被前者咬到：兩個視窗排了約一個半小時，那天 4,706 個請求，
而那台服務前 15 天全部加起來一百多個。免費額度是一天 100,000 —— 一個玩家
兩個視窗就能吃掉七成，而且全部發生在「沒有人真的在配對」的狀態下。

所以 `match-client.ts` 現在分兩種情況：

- **一次都沒連上過** → 退避重試五次（約一分鐘）就**停下來**，狀態 `unreachable`，
  配對停在 `blocked` 並告訴玩家去看位址。位址錯或服務沒部署再試一萬次也一樣
- **連上過又斷線** → 繼續退避重試（上限 60 秒），因為玩家還在等配對，而網路
  抖一下是會自己好的

### 配對任務什麼時候結束

**對戰一開始就結束**，不用玩家按停止。這件事對 host 特別重要：他開完房之後
如果還留在佇列上，中間人會把**第三個人**配給他，而他已經在打了。

| 角色  | 結束的判準                                             |
| ----- | ------------------------------------------------------ |
| host  | 自己那間房多了 playerB，或那間房從清單上消失（已開打） |
| guest | `joinRoom` 成功                                        |

host 那邊的判準刻意**看遊戲不看佇列**：對手的插件一進房就會離開佇列，而離開
佇列送的是 `q-cancel` —— 在佇列眼裡跟「他按了停止」一模一樣。照 `q-dropped`
處理的話會在對手剛進門的瞬間把房拆掉，然後去排下一個人，畫面上還寫著
「對手取消了，繼續排隊」。2026-08-16 實測到的就是這句話，而那一場已經打起來了。

⚠ `gone`（連線真的斷了）仍然照舊收房退回佇列 —— 那是真的走了。
⚠ 逾時（90 秒）沒人進來就收房並停止，不能留一間永遠沒人進的空房。

### 開始配對時會先收掉你自己開著的房

preflight 本身是唯讀的（手動那條路也用它），但**自動配對會先收再排**：擋住的
那間房多半就是插件上一輪自己開的（對手沒進來、或上一場打完了），而叫玩家
「請先去遊戲裡收掉」對他沒有意義。

⚠ `delete_room` 是**頻道層級**的 —— 它會把你在那個頻道的房**全部**收掉，
包含手動開的。所以這件事一定會寫進記錄檔。

### 驗算沒過會怎樣

送 `q-reject`：兩個人都留在佇列裡，而**中間人會記住這一對試過了**。

⚠ 少了這張清單，兩個規則對不起來的人會在 FIFO 裡被立刻重新湊成同一對，
然後再次失敗、再次退回 —— 一個以毫秒為單位的無窮迴圈，而兩邊的畫面上只會看到
「配對中」一直閃。清單記的是連線 id，所以對方重連之後可以再配一次（中間人
**刻意沒有身分概念**，記得更久需要身分）。

## 5. 約定的 COST 上限由誰檢查

**雙方各自檢查自己那副牌，沒有人審對方。**

遊戲自己的「牌組Cost限制 ±N」是伺服器用**原版 COST** 判的，跟自訂規則算出來的
數字對不上 —— 它擋不掉「這副牌在燈皇規則下是 68C」。所以上限這件事只有插件
做得到，而做法是：

- 上限**進配對鍵**（填得不一樣的人排在不同佇列，永遠配不到）
- 排隊前、以及每一次配到人時，各自用約定的規則算**自己**那副牌
- 超標就停下來並告訴玩家要改什麼，**不會**去看對手多少 C

兩邊都會拒絕不合法的自己，所以不需要互相審查 —— 也就不需要把對手的總和顯示
出來，而那正是「先看看對手多少 C 再決定要不要打」的入口。

### 官方的 COST 檔位只是快速鍵

自訂 COST 想約幾就填幾 —— 但**平常對戰最常約的就是官方那幾檔**，所以配對頁把
它們列成按鈕，省得每次自己打數字。

⚠ **duel 頻道自己沒有檔位。** 2026-08-16 兩個客戶端實測（59222 迪特、9334 亞城）：

```
channels       = {"1":{type:"ranked",cost:[57,66,78]}, "2":{type:"duel"}}
channels_cross = {"3":{type:"ranked",cost:[56,69,71]}, "4":{type:"duel"}}
```

2 與 4 **連 `cost` 這個鍵都沒有**。玩家給的規則是「頻道二用亞歷山卓城的、頻道四
用峰亥盧遺跡的」，而實測的結構比那個對映更基本：`channels` 與 `channels_cross`
是**兩組各自成套**的頻道（各走一條 socket），每組裡一個 ranked 一個 duel，
duel 借同組 ranked 的。`costTiersFor()` 照這個結構推導。

⚠ **不要寫死成 `{2:1, 4:3}`。** 官方哪天多開一組頻道，寫死的版本會安靜地拿到
另一組的數字 —— 而 1 是 `[57,66,78]`、3 是 `[56,69,71]`，**兩組真的不一樣**，
拿錯不報錯，只會讓兩個人約定到不同的上限然後配不到彼此。

⚠⚠ **這些數字每週二遊戲更新會跟著變**，所以插件每次都從玩家自己的客戶端現讀，
不快取、不寫進設定檔、更不烤進程式碼。存起來的症狀是「明明兩個人都按了 57
卻永遠配不到」—— 一邊用上週的、一邊用這週的，算出不同的配對鍵。

## 5a. 頻道要看兩次

房間清單是**分頻道推播**的，所以「兩個人都在同一個頻道」不是設定問題，是這件事
成不成立的前提。頻道因此進配對鍵，而且要檢查兩次：

| 什麼時候             | 檢查什麼                                             |
| -------------------- | ---------------------------------------------------- |
| 按下「開始自動配對」 | 玩家在頻道裡嗎（沒有的話直接說「請先進入一個頻道」） |
| **每次配到人**       | 玩家**還**在那個頻道嗎                               |

第二次不能省 —— 排隊是會等的，玩家完全可能在等的時候切去別的頻道。少了那一關
的症狀分兩種，兩種都很難懂：host 會在新頻道開一間房（對手在舊頻道根本看不到
它），guest 會在新頻道的清單裡找一個不存在的 room_id 找到逾時。

---

## 6. 判斷在客戶端，為什麼這仍然是安全的

換成語義驗算之後，判斷從「物理上碰不到」變成了客戶端自己算。改過的插件可以
跳過驗算嗎？可以，但**沒有用**：

- 開房的是 host、進房的是 guest，**兩邊都得各自走完自己那半段**
- 對手的插件會獨立算一次，算不過就不會進來

所以要繞過去必須**兩邊都改過**，而那時他們本來就是講好的 —— 兩個講好的人從來
就可以不裝插件直接開房。這跟準備／秒數協商是同一條原則：**會改變勝負的東西
一律要雙方都同意才生效**。

---

## 7. 對手的牌組不會出現在畫面上

跨版本驗算要交換牌組描述子，所以插件**知道**對手帶了哪三隻。它只拿去算指紋，
然後就丟掉：

- 不放進 `PairingStatus`（UI 唯一看得到的東西）
- 不寫進記錄檔
- 沒有任何介面問得到它

這不是隱藏資訊的問題 —— 房間清單本來就把雙方牌組（含 `chara`、`charaIndex`、
`cost`）廣播給大廳裡**每一個人**，MatchingLobby 的房間列確實會畫出雙方的卡片
縮圖。這是**運動精神**的問題：看得到對手帶什麼就能挑對手，而那會讓整個約戰
功能失去意義。

⚠ 同一份規則的配對（絕大多數）根本不會走到交換那一步 —— `EXACT` 快路存在的
理由一半是效能，一半是這個。

### 中間人看得到什麼

誠實地列：

| 東西               | 中間人看得到嗎                                                           |
| ------------------ | ------------------------------------------------------------------------ |
| 配對鍵             | ✅ 但它是雜湊，看不出是哪份規則                                          |
| 規則標籤           | ✅ 同上，而且拌了配對鍵，換一條佇列就是另一個字串                        |
| 牌組描述子         | ⚠ **它經手**（`q-deck` 的 `body`）。它不解讀，但那是設計選擇不是數學保證 |
| 玩家身分、房號原文 | ❌ 從來不上去                                                            |

⚠ **這裡跟房號那條的保證強度不一樣，不要混為一談。** 房號是雜湊過的，
「中間人認不出那是哪一場」是數學問題；牌組描述子是明文轉發的，「中間人不看」
是它的行為。要更強的保證只有兩條路：端對端加密（雙方沒有共同祕密可以派生，
token 是中間人自己產的），或是由一台**保存所有規則版本**的伺服器代算
（那是 ULGG 的角色，WP-03 之後才可能）。

現階段的取捨是：**跨版本相容只在 `EXACT` 不成立時才交換，而交換的內容在幾秒後
就會由遊戲自己公開廣播給整個大廳。**

## 8. 還沒做的

- **武器與事件卡不在描述子裡。** 它們的正規鍵還沒定案
  （[open-questions.md](open-questions.md) 第 1 題：`entityId` 仍是寬鬆的
  pattern）。把還沒定案的東西寫進描述子，會讓兩個版本的插件對同一副牌算出
  不同的鍵 —— 症狀是「規則明明一樣卻說不相容」。定案之後加欄位並把
  `EVALUATION_FORMAT_VERSION` 加一。
- **戰果不會標記相容性。** 跨版本打完的那一場應該記成 `1.5.0 × 1.5.1` 而不是
  塞進其中一版，否則 Character Analysis 的版本統計會失真。那是 WP-05／WP-06
  的事（ULGG 端）。
- **本機 broker 沒有佇列。** 玩家把中間人設成 `local` 時自動配對連不上 ——
  那個組合是雙開測試用的，`broker.ts` 只認得房間協定。
- **牌組是配對當下讀的。** 玩家在「驗算完」到「房開好」之間換牌組的話，實際
  打的會是新的那副。這個窗口關不掉（送出開房封包的是遊戲自己），但它需要
  玩家刻意在幾秒內操作。
