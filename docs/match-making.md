# 自動配對與跨版本相容（WP-16）

「兩個約定同一套 COST 規則的人，自動湊成一場有密碼的自訂房。」

這份文件回答三個問題：

1. 為什麼配對需要中間人 —— 遊戲自己的佇列做不到這件事
2. 為什麼「規則 hash 一樣」**不能**當成配對的條件
3. 那要拿什麼當條件，以及那樣還安不安全

> **要做的是亞歷山卓城的快速比賽，不是「約戰」。** 這個定位決定了三件會讓人
> 意外的設計：檔位**有下限**（§5）、房名**玩家取不到**（§5b）、地圖**選不到**
> （§4「對戰地點」）。三件事在亞城都不是選項，而它們正是「按一顆按鈕就開打」
> 跟「先填一張表」的差別。

---

## 1. 為什麼要有中間人

遊戲自己有快速比賽，但實測 `on_server_status` 之後就知道它用不上：

```
channels = { "1": { type: "ranked", cost: [57,66,78] },   ← 亞歷山卓城
             "2": { type: "duel" } }                       ← 迪特赫姆
```

`quick_wait` 是**伺服器端**的佇列，只有 ranked 頻道有，而且 COST 階層是伺服器
定的（用**原版 COST** 判）。自訂規則的約戰只能發生在 duel 頻道，那裡沒有佇列。

所以在有中間人之前，「約戰」只能是：開一間房、把房號與密碼用 Discord 傳給對手。
那是**認識的兩個人**才能做的事，而自訂 COST 規則要成為一個環境，需要陌生人也
配得到彼此。

中間人（`apps/link-worker`）因此多了第二條路徑：

| 路徑                 | 什麼時候連                       | 一個實例是什麼              |
| -------------------- | -------------------------------- | --------------------------- |
| `wss://…/r/<房號>`   | 對戰中                           | 一間對戰房（側通道，WP-15） |
| `wss://…/q/<配對鍵>` | **玩家按下「開始自動配對」之後** | 一條配對佇列                |

兩條走同一台伺服器、同一套訊息大小與流量限制，玩家的設定裡只有一格。

## 2. 為什麼配對鍵不能是規則的 hash

第一版的配對鍵是這樣算的：

```
matchKey = sha256(contentHash | 頻道 | 3vs3 | COST 上限)
```

`contentHash` 是整份規則內容的 SHA-256。這個設計有一個很漂亮的性質：
**規則不一樣的人算出不同的鍵，落在不同的 Durable Object，物理上碰不到對方** ——
不需要任何一方自律，也不需要中間人比對什麼。

它的問題是把「版本相同」當成了「可以一起打」的必要條件，而那不成立：

```
版本 A                     版本 B
  R3 利恩   = 22             R3 利恩   = 22
  R3 艾伯   = 18             R3 艾伯   = 18
  R3 阿貝爾 = 17             R3 阿貝爾 = 17
  新角色 X  = 25             新角色 X  = 26   ← 只差這一個
```

雙方都帶利恩＋艾伯＋阿貝爾出戰。兩邊算出來的每一個數字都一樣，
**「X 是 25 還是 26」對這一場沒有任何可觀測的影響** —— 但整表 hash 不同，
於是他們永遠配不到對方。

規則作者每發一次版就把社群切成兩半，而切開的理由是一個沒有人帶上場的角色。
這叫版本碎片化，不是公平性。

### 真正要問的問題

不是「兩份規則是不是同一份」，而是

```
Eval(這一場的牌組, 規則 A) == Eval(這一場的牌組, 規則 B)
```

也就是**局部語義等價**。所以身分拆成三層，而**只有第三層是配對的閘門**：

| 層                   | 是什麼                           | 用途                 | 在哪               |
| -------------------- | -------------------------------- | -------------------- | ------------------ |
| `contentHash`        | 整份規則的 SHA-256               | 版本識別、統計、稽核 | `@ulr/rule-schema` |
| 配對鍵               | `ruleSetId` + 頻道 + 3vs3 + 上限 | 決定排在哪一條佇列   | `matchKey()`       |
| **`evaluationHash`** | **這一場的完整計算結果**         | **這一場能不能成立** | `@ulr/cost-engine` |

配對鍵裡放的是 `ruleSetId`（`publisherSlug/ruleSlug`），所以**同一套規則的不同
版本會排在同一條佇列**，不同規則（燈皇 vs 亞城）仍然物理上碰不到。

⚠ 那個 `3vs3` 欄位現在是**固定值**（永遠 `multi`，見 `ROOM_MULTI`）—— 插件開的房
一律 3vs3，玩家選不到。欄位留在鍵裡是因為**格式一發布就不能改**：拿掉它會讓舊版
與新版算出不同的鍵，而症狀是安靜地配不到人。

## 3. 語義指紋蓋的是整份計算結果，不是總和

只比總和會出事：

```
規則 A：20 + 20 + 20，壓 C −2  → 58
規則 B：19 + 20 + 19，壓 C  0  → 58
```

總和一樣，單角 COST 完全不同。之後任何看單角數字的限制或畫面都會產生歧義。

所以指紋蓋的是逐角定價、逐對壓 C、未定價清單、規則宣告的上限、總和：

```jsonc
{
  "v": 1,
  "characters": [
    ["abel_r3", "17.00"],
    ["evarist_r3", "18.00"],
    ["leon_r3", "22.00"],
  ],
  "compression": [["abel_r3", "leon_r3", "5.00", "5.00"]],
  "unknown": [],
  "limit": "62.00",
  "total": "62.00",
}
```

正規化之後取 SHA-256 —— **跟規則的 contentHash 是同一套 RFC 8785 (JCS)**，
所以 ULGG 那邊（PHP）照 [canonical-json.md](canonical-json.md) 實作就對得上。

三件事值得單獨講：

- **角色鍵會排序。** 槽位順序是玩家在牌組畫面上排的，它不影響任何計算
  （壓 C 是每一對各判一次），卻會讓指紋不同。
- **數值是固定兩位小數的字串**，不是數字。浮點的尾巴會讓兩台電腦算出不同的
  字串（`8.8 + 26.6 + 26.6` 是 `62.00000000000001`）。
- **`teamCostLimit` 與壓 C 區間也在裡面。** 兩份規則只差在上限也是真的差異：
  同一副牌在一邊合法、另一邊超標，那不是同一場比賽。

### ⚠ 要算四次，不是兩次

「甲用 A 算自己 = 57，乙用 B 算自己 = 57」證明不了什麼。要成立的是交叉的四次：

```
Eval(A, 甲牌) == Eval(B, 甲牌)   且   Eval(A, 乙牌) == Eval(B, 乙牌)
```

只驗自己那副的話會發生這種事：

```
甲的牌   規則 A → 60    規則 B → 61
乙的牌   規則 A → 59    規則 B → 60
```

兩人各自看到的數字都「合理」，但他們身處不同的規則宇宙 —— 同一場比賽裡，
對手的隊伍在我眼中是 60、在他眼中是 61。

## 4. 完整流程

```
  host                        佇列                        guest
   │── q-hello(鍵, 規則標籤) ──▶│◀──────────── q-hello ─────│
   │◀── q-matched(角色, token, 對手標籤) ── q-matched ─────▶│
   │                           │                           │
   │  標籤一樣 → EXACT，跳到開房（牌組完全不交換）           │
   │                           │                           │
   │── q-deck(我的描述子) ─────▶│◀──────── q-deck ──────────│
   │◀── q-deck(對手的) ────────│──────── q-deck ──────────▶│
   │  各自用**自己那份規則**算兩副牌 → 兩個指紋              │
   │── q-eval(host指紋, guest指紋) ▶│◀────── q-eval ────────│
   │  四個指紋兩兩相等 → COMPATIBLE，否則 INCOMPATIBLE      │
   │                           │                           │
  建房(pass=token)             │                           │
   │── q-room(roomId) ────────▶│──────── q-room ──────────▶│
   │                           │                    進房(roomId, token)
```

`token` 同時是**房間密碼**（遊戲自己的密碼就是 8 碼英數，格式一致），所以外人
看得到那間房卻進不去。⚠ **房名絕對不能包含 token** —— 房名是公開的。

三態的結果：

| 判決           | 意思                                              |
| -------------- | ------------------------------------------------- |
| `EXACT`        | 兩邊的 `contentHash` 就是同一個。不必交換任何東西 |
| `COMPATIBLE`   | 規則不同，但這一場的四次計算完全一致              |
| `INCOMPATIBLE` | 至少有一副牌在兩份規則下算出不同的東西            |

### ⚠ 中間人必須是**部署過佇列**的那一版

`/r/<房號>`（側通道）與 `/q/<配對鍵>`（佇列）是同一台 Worker 的兩條路由，但
**它們是分開上線的** —— 側通道早就在跑，佇列是 WP-16 才加的。所以會出現這種
狀態：房間側通道一切正常、自動配對卻永遠配不到，因為 `/q/` 回 404。

```powershell
# 這一條就是在問「那台有沒有佇列」
curl.exe -i https://ulr-link.lldavuull.workers.dev/q/0123456789abcdef
#   426 expected websocket → 有（正常，因為 curl 沒帶 Upgrade）
#   404 not found          → 沒有，要重新部署
npm --workspace apps/link-worker run deploy
```

2026-08-16 實測就是這個：兩個客戶端條件完全相同（頻道 2、同一份 shinon 規則、
上限 57），畫面兩邊都寫「排隊中 · 只有你」，而那台 Worker 還是沒有佇列的舊版。

> ⚠ 插件那邊的症狀**完全沉默**是另一個 bug，已經修掉：`phase` 在按下按鈕的
> 當下就被設成 `queued`，而 WebSocket 那時才剛開始連。現在 `PairingStatus.linked`
> 只有在收到 `q-welcome` 之後才是 true，畫面會分開講「還沒連上中間人」與
> 「排隊中，只有你」，記錄檔也會印連不上的那幾行。

### 排隊不是輪詢 —— 但重連是

配對**沒有任何輪詢**。連上去是一個請求，之後那條 WebSocket 就一直開著，
中間人主動推 `q-matched` / `q-deck` / `q-room` 過來；插件也沒有心跳。
一場配對從頭到尾對雲端來說就是**一個請求**，之後的訊息走 Durable Object
（而且進 hibernation，閒置不計時間）。

會產生流量的是**連不上時的重試** —— 那不是在問「配對好了沒」，是在試著把
訂閱建立起來，而一台回 404 的伺服器你沒辦法向它訂閱任何東西。

| 版本                  | 卡住一天的請求數 |
| --------------------- | ---------------- |
| 固定 2 秒重試（原本） | 43,200           |
| 指數退避，上限 60 秒  | 1,440            |

2026-08-16 就是被前者咬到：兩個視窗排了約一個半小時，那天 4,706 個請求，
而那台服務前 15 天全部加起來一百多個。免費額度是一天 100,000 —— 一個玩家
兩個視窗就能吃掉七成，而且全部發生在「沒有人真的在配對」的狀態下。

所以 `match-client.ts` 現在分兩種情況：

- **一次都沒連上過** → 退避重試五次（約一分鐘）就**停下來**，狀態 `unreachable`，
  配對停在 `blocked` 並告訴玩家去看位址。位址錯或服務沒部署再試一萬次也一樣
- **連上過又斷線** → 繼續退避重試（上限 60 秒），因為玩家還在等配對，而網路
  抖一下是會自己好的

### 對戰地點：玩家選不到地圖，只選「誰來抽」

**指定地圖這個選項拿掉了。** 亞城的快速比賽不讓人挑地圖，而挑地圖在這裡也不
成立：開房的只有 host，所以「我指定 007」對 guest 而言永遠是被決定的。舊版的
協商（從雙方各選的兩張裡抽一張）只是把那個不對稱換成擲骰子 —— 兩個人仍然都
可能被丟到自己沒選的地方，只是多了一顆骰子。

剩下的選擇是**抽的池子**：

| 值         | 誰抽       | 池子                                       |
| ---------- | ---------- | ------------------------------------------ |
| `arcadia`  | **插件**   | `000`~`010`，**11 張**（`ARCADIA_STAGES`） |
| `official` | 遊戲伺服器 | 它自己那份（送 `014`）                     |

⚠ **亞城池含 `010`（魔女山谷），那是官方開房選單裡選不到的一張**（見
`HIDDEN_STAGES`）。客戶端與伺服器都認得它、背景圖也實測抓得到，但**還沒有在
上面打完一整場**。不想碰的人選「官方隨機」。

配到人時兩邊各送一則 `q-pref`（跟 `q-deck` 走同一條不透明轉發），host 收到之後：

| 我       | 對手             | 結果             |
| -------- | ---------------- | ---------------- |
| arcadia  | arcadia          | 從那 11 張抽一張 |
| arcadia  | **沒說**（舊版） | 從那 11 張抽一張 |
| arcadia  | official         | **`014`**        |
| official | 任何             | **`014`**        |

⚠ **只要有一邊選了「官方隨機」就走官方隨機。** 那一邊等於說了「不要插件替我
抽」，而亞城池裡有一張官方選單沒有的地圖 —— 硬把他丟過去是拿他沒同意的東西
去改變這一場。反過來沒有這個問題：官方隨機抽到的一定是官方認得的地圖。

⚠ host 最多等 3 秒（`STAGE_WAIT_MS`）。等不到就用自己的開下去 —— 地點協商是
加分，不是開打的前提。

⚠ **`q-pref` 要中間人轉發**，所以那台也得是新版。舊版不轉的話兩邊都收不到對方
的偏好，於是各自退回「用 host 的」，功能靜靜地消失但不會壞。

⚠ **跟舊版插件的相容是刻意設計的**：`official` 送的是 `"014"` 而不是
`"official"`，因為舊版的 `parsePrefBody` 只收三位數字 —— 它讀得懂 `014`，於是
舊版當 host 時也會開隨機房。`arcadia` 沒有對應的舊值，送過去被當成「他沒說」，
舊版就用他自己的，那是正確的退化。反過來，舊版送來的三位數字一律當成
`official`：新版沒有「指定某一張」這個概念了，照他指定的那張開等於讓一個舊版
客戶端單方面決定地點。

### 插件不提供手動開房

地點、Cost 限制那幾格**只服務自動配對** —— 它們是「配到人之後要怎麼開房」。

手動開房遊戲自己就做得很好，而插件多一條路只會跟自動配對搶房間：`delete_room`
是**頻道層級**的，玩家手動開一間、插件再開一間，之後任何一邊的「取消」都會把
兩間一起收掉（2026-08-15 實測）。

### 配對任務什麼時候結束

**對戰一開始就結束**，不用玩家按停止。這件事對 host 特別重要：他開完房之後
如果還留在佇列上，中間人會把**第三個人**配給他，而他已經在打了。

| 角色  | 結束的判準                                             |
| ----- | ------------------------------------------------------ |
| host  | 自己那間房多了 playerB，或那間房從清單上消失（已開打） |
| guest | `joinRoom` 成功                                        |

host 那邊的判準刻意**看遊戲不看佇列**：對手的插件一進房就會離開佇列，而離開
佇列送的是 `q-cancel` —— 在佇列眼裡跟「他按了停止」一模一樣。照 `q-dropped`
處理的話會在對手剛進門的瞬間把房拆掉，然後去排下一個人，畫面上還寫著
「對手取消了，繼續排隊」。2026-08-16 實測到的就是這句話，而那一場已經打起來了。

⚠ `gone`（連線真的斷了）仍然照舊收房退回佇列 —— 那是真的走了。
⚠ 逾時（90 秒）沒人進來就收房並停止，不能留一間永遠沒人進的空房。

### 開始配對時會先收掉你自己開著的房

preflight 本身是唯讀的（手動那條路也用它），但**自動配對會先收再排**：擋住的
那間房多半就是插件上一輪自己開的（對手沒進來、或上一場打完了），而叫玩家
「請先去遊戲裡收掉」對他沒有意義。

⚠ `delete_room` 是**頻道層級**的 —— 它會把你在那個頻道的房**全部**收掉，
包含手動開的。所以這件事一定會寫進記錄檔。

### 排隊途中玩家跑掉了怎麼辦

排隊是**會等的**，而玩家在等的時候會去做別的事。所以排隊期間插件每 5 秒
（`LOBBY_WATCH_MS`）問一次遊戲他還在不在：

| 看到什麼               | 做什麼                           |
| ---------------------- | -------------------------------- |
| 不在 Match 場景了      | **停止排隊**（他被拉進對戰了？） |
| 退出頻道了             | **停止排隊**                     |
| 換到別的頻道了         | **停止排隊**                     |
| 自己開了一間房         | **照排不誤**                     |
| 問不到（CDP 抖、重載） | 當這一輪沒看到，下一輪再問       |

前三件事少了這一段的症狀是一樣的：那條佇列連線一直掛著，等他打完回到大廳，
中間人早就把他配給某個人了 —— 而那個人開了一間房，正在等一個根本沒在看畫面
的對手。（配到人**當下**還是會再確認一次頻道，那一關不能省，但它太晚了。）

⚠ **「玩家自己開了一間房」不是停止的理由。** 那是他的事，而且他多半就是想
兩邊碰運氣。真的配到人時插件才幫他收掉那間 —— host 那半段是 preflight 順手
收的，guest 那半段**沒有 preflight**，所以 `#clearOwnRoom` 要自己叫一次。少了
它，玩家人進了對手的房，自己那間會留在清單上等一個永遠不會來的人，而下一次
配對會被「你已經有一間自己開的房」擋住。

⚠ **只在 `queued` 的時候看。** 開房、進房那幾段離開 Match 場景是正常的 ——
進房成功的下一刻遊戲就切到對戰畫面了。在那裡判「他不在大廳」等於把剛打起來的
一場自己收掉，而畫面上會寫「你不在大廳了」。

### 驗算沒過會怎樣

送 `q-reject`：兩個人都留在佇列裡，而**中間人會記住這一對試過了**。

⚠ 少了這張清單，兩個規則對不起來的人會在 FIFO 裡被立刻重新湊成同一對，
然後再次失敗、再次退回 —— 一個以毫秒為單位的無窮迴圈，而兩邊的畫面上只會看到
「配對中」一直閃。清單記的是連線 id，所以對方重連之後可以再配一次（中間人
**刻意沒有身分概念**，記得更久需要身分）。

## 5. 約定的 COST 檔位由誰檢查

**雙方各自檢查自己那副牌，沒有人審對方。**

遊戲自己的「牌組Cost限制 ±N」是伺服器用**原版 COST** 判的，跟自訂規則算出來的
數字對不上 —— 它擋不掉「這副牌在燈皇規則下是 68C」，反過來還會擋掉一副照約定
完全合法的牌組。所以插件開房時**永遠不設它**（`ROOM_DECK_COST_BAND`），玩家也
沒有那一格。檔位這件事只有插件做得到，而做法是：

- 檔位**進配對鍵**（填得不一樣的人排在不同佇列，永遠配不到）
- 排隊前、以及每一次配到人時，各自用約定的規則算**自己**那副牌
- 不在這一檔裡就停下來並告訴玩家要改什麼，**不會**去看對手多少 C

兩邊都會拒絕不合法的自己，所以不需要互相審查 —— 也就不需要把對手的總和顯示
出來，而那正是「先看看對手多少 C 再決定要不要打」的入口。

### 5a-2. 迪特赫姆大廳裡那顆「快速比賽」（WP-17）

托盤上那顆按鈕還在，但**玩家實際會按的是遊戲畫面裡這一顆** —— 它畫在
「創建對戰室」左邊，長得跟亞城那顆一模一樣（同一張 `match_quick_btn`、
同一個按鈕類別）。實作在 `@ulr/cdp-adapter` 的 `patch-lobby.ts`。

兩顆按鈕的差別只有一個，而那個差別是重點：

| 入口         | 檔位怎麼決定                                      |
| ------------ | ------------------------------------------------- |
| 托盤的配對頁 | 玩家自己在設定裡填的那一格（約戰的用法）          |
| **大廳那顆** | **照牌組自己算**（`tierForTotal`）—— 亞城就是這樣 |

按下去之後：

```
   讀牌組 → 用約定的規則算總和 → 落在哪一檔？
                                   ├─ 有 → 排進那一檔的佇列
                                   └─ 沒有 → 跳遊戲自己的
                                             「這個牌組不符合遊戲規則」
```

⚠ **那句話是 `Match.room_error[lang][7]`，對話框也是遊戲自己那個類別**
（webpack 模組裡撈出來的）。玩家在亞城帶一副不合檔的牌時看到的就是它 ——
自己畫一個像的框，第一眼就會被看出來是外掛的東西。

⚠ **排隊中跳的是遊戲自己的等待視窗**（`Match` 模組裡的 `class S`：面板 +
逐字波浪的「正在等待對手加入…」+ MM:SS + `cancel` 鈕），不是在 INFO 區多寫
一行字。那個框才是亞城按下快速比賽之後會看到的東西，而「我到底在不在排隊」
這件事上，一行小字跟一個會計時的視窗完全不是同一種東西。
按 `cancel` 跟再按一次「快速比賽」走**同一條**回報路徑（`lobby-quick`）——
兩個入口不該有兩套邏輯。

### 5a-3. 等待人數：`COST54:1位玩家等待中。`

亞城的 INFO 區有四行人數，迪城沒有 —— 因為那是伺服器推的 `channel_players`，
而 **duel 頻道伺服器不推**。插件把那幾行補回去，資料換成中間人的佇列人數。

#### 推播（主要的路）

玩家坐在大廳時，每一檔各開一條 WebSocket 到自己那條佇列（`/q/<鍵>`），
送一則 `q-watch` 就不再說話；**中間人一有人進出就推一則 `q-count` 回來**。

```
   插件 → q-watch  { v, key, tag? }     「我只看，不要把我排進去」
   中間 ← q-count  { waiting }          接上時一則，之後每次有人進出一則
```

⚠⚠ **`q-watch` 的人不進 `MatchQueue`。** 那個類別是配對規則，把看的人放進去
會讓他被湊成一對 —— 而他人在大廳，根本沒按任何東西。看的人只掛在 DO 的
socket 清單上（attachment 裡的 `watch`，hibernation 醒來要認得出來）。

⚠ **這才是「立即反應」。** 輪詢版本有一個結構上治不好的毛病，而它就是玩家
2026-08-20 回報的那兩句 ——「一邊開始匹配，另一邊要等 15 秒」「按下取消也是
等 15 秒」。注意兩句講的都是**另一邊**：自己那一邊早就是即時的了（`displayCounts`
把「我」算進去），慢的是別人的動作傳到我畫面上這條路，而輪詢的間隔就是那條路
的長度。把它調到 3 秒只是把帳單乘以五，而且還是慢 3 秒。

| 作法       | 一小時的請求數 | 別人按下去多久看得到 |
| ---------- | -------------- | -------------------- |
| 輪詢 15 秒 | 240            | 最久 15 秒           |
| 輪詢 3 秒  | 1,200          | 最久 3 秒            |
| **推播**   | **接上去一次** | **立刻**             |

四條連線看起來比一個 HTTP 請求貴，實際上反過來：接上去之後**沒有人動就完全
沒有訊息**，而輪詢是不管有沒有人動都要付錢的（CF 的 hibernation 讓閒置的
WebSocket 不算時間）。玩家離開大廳（打牌、進選單、關遊戲）就把線收掉。

#### 輪詢（退路，還留著）

```
   GET https://…/qn?k=<鍵1>&k=<鍵2>&…&t=<標籤1>&t=<標籤2>&…
   → { counts: [ { key, waiting }, … ] }
```

⚠⚠ **舊中間人收得下那條連線，但不會回話** —— `q-watch` 它解不出來，於是線
就這樣開著。少了逾時的話插件會安靜地等一則永遠不會來的 `q-count`，而畫面上
那幾行**整個不見**（比慢 15 秒糟）。所以：送出去 10 秒內沒有 `q-count` 就
判定這台推不了，關線、不重試、退回輪詢。

推播接得上時輪詢不會停掉，只是拉長到 **120 秒**當保險 —— 一條「開著但對面
已經不在」的 WebSocket 是真的會發生的，而它的症狀（人數停住不動）跟「真的
沒人」長得一模一樣。

⚠ **一個請求問完所有檔位。** 一檔一個請求等於把量乘以四（§4 那張
43,200 vs 1,440 的表是同一件事）。只有在**玩家真的坐在 duel 頻道的大廳裡**
才會發（`buttonReady`）。

#### 只數「跟我同一份規則」的人

⚠⚠ 兩條路都帶 **規則標籤**（`t=`／`q-watch` 的 `tag`），而中間人只數標籤
一樣的人。配對鍵裡**沒有規則版本**（那是刻意的，見 §3），所以同一條佇列上
站著規則內容不同的人是常態 —— 他們配不配得到要看驗算。畫面上寫
「1 位玩家等待中」而那個人永遠配不到，**比寫 0 還糟**：玩家會一直等，然後
以為插件壞了。

⚠ 標籤是 `ruleTag(配對鍵, contentHash)` —— **拌過配對鍵**，所以同一份規則在
四個檔位上是四個不同的字串（去連結，見 §3）。因此 `t=` 是一份**跟 `k=` 對齊
的清單**，不是一個值；數量對不上一律 400，錯位的話每一檔都會拿一個不屬於它
的標籤去比，結果全部數到 0 而且沒有任何錯誤訊息。

⚠⚠ **只有用預設 COST 表的人才有這幾行數字**（2026-08-20 的決定）。自己選了
規則檔的人看不到 —— 那不是壞掉，是那個數字對他沒有意義：他排的是一條只有他
自己那份規則算得出來的隊。判準是 `costRuleOrigin === "file"` 而不是設定裡的
模式，因為下載來的規則壞掉時會退回安裝包那份，兩者會不一致。

#### 其他

⚠ **人數那幾行用的是遊戲自己的模板**（`PLAYER_COUNT[lang][1]`），我們只填數字。
自己組字串的話換一種語言就會露出繁中。

⚠ **那幾行接在 `player_count` 底下的位置要每次重算，不要沿用掛上去那一刻的值。**
官方那一版（`refresh_ranked_players`）就是每次 `setPosition` 重算的。2026-08-20
實測到後果：一台的快取值卡在 506 而 `player_count` 的底部是 488 —— 於是
`COST54` 上面空了一列。

⚠ **問不到人數時要保留上一次的數字，不能推 `null` 把它清掉。** 中間人抖一下
就把那三行洗掉的話，玩家看到的是「人數忽有忽無」，那比慢個 15 秒難懂得多。

⚠ 中間人那條 `/qn` 與 `q-count` 是**這台伺服器唯一會說出去的佇列狀態**，而它
是刻意開的例外（`/health` 那條的規則是「不回任何跟房間有關的東西」）。理由有
兩個：它是**一檔的人數**而不是身分，而且**遊戲自己就公開這個數字**。

### 5a-4. `COST90+`：那一檔沒有上限，改用 ±5 的窗口

亞城的第四行是 `COST90+`，而它跟前三檔不是同一種東西 —— 沒有上限可言。
玩家給的規則：**95C 配得到 90～100C**。所以那一檔的作法不一樣：

|                  | 有上限的檔（54/61/77）     | 開口檔（90+）                      |
| ---------------- | -------------------------- | ---------------------------------- |
| 誰跟誰同一條佇列 | 同一檔的人（檔位進配對鍵） | **90 以上的人全部排同一條**        |
| 配對條件         | 排在一起就是條件成立       | 配到之後再看**兩副牌差幾 C**（±5） |
| 房名             | `[COST:57]`                | `[COST:90+]`                       |

⚠⚠ **開口檔一定要交換牌組，`EXACT` 快路在那一檔不能走** —— ±5 要算對手的
總和才判得出來。算出來的數字**只當閘門**：不進畫面、不進記錄檔（§7 那條線），
訊息也只說「差太多」，不說對手幾 C。

⚠ 差太多時送 `q-reject`，兩個人都留在佇列裡而中間人會記得「這一對試過了」——
跟規則不相容走同一條路。少了那張清單，兩個差 8C 的人會在 FIFO 裡被立刻重新
湊成同一對，變成毫秒級的無窮迴圈。

⚠ **90 這個數字是從遊戲自己的模板讀的**（`PLAYER_COUNT` 裡那個 `COST90+`），
不是寫死在插件裡。官方哪天改成 100+，寫死的那一版會安靜地排到另一條佇列上，
而兩邊畫面都寫著「排隊中」。

⚠ 三檔之間與 77～90 之間的**縫是真的縫**：80C 的隊伍不落在任何一檔，按下去
就是「這個牌組不符合遊戲規則」。那跟「幫他挑最接近的一檔」是兩回事 ——
後者等於把下限拿掉，而下限正是壓 C 這件事存在的理由。

### ⚠⚠ 檔位有下限，不是「小於等於」

約定 57 收的是 **56.01～57.00**，不是「57 以下」。這跟亞歷山卓城的 `COST57`
是同一個意思，而自動配對就是要取代那個。

```
   ├──── 56 檔 ────┤├──── 57 檔 ────┤├──── 58 檔 ────┤
  55.01         56.00 56.01       57.00 57.01       58.00
```

沒有下限的話「57 檔」會收下一副 40C 的隊伍，而 40C 打 57C 不是一場比賽。更根本
的理由是：**自訂 COST 規則整套東西的重點是壓 C** —— 把隊伍擠到剛好卡滿那一檔。
而「壓到剛好」只有在下限存在時才是一件要花心思的事；沒有下限的話帶什麼都合法，
那個設計空間整個消失。

⚠ 下限是 `上限 − 1.00 + 0.01` 而不是 `上限 − 1.00`：**兩檔不重疊**，56.00 屬於
56 檔而不是 57 檔，一副牌永遠只落在一檔裡。

⚠ 一律走 `toCentiCost` 轉成整數再比。`limit - 1` 在浮點上是 `56.00000000000001`，
而那會讓剛好卡在下限的隊伍被判成太低 —— 那是 `cost-number.ts` 整支檔案存在的
理由，而且這裡有**兩個**邊界要守，不是一個。

⚠ 擋下來的訊息**一定要說得出方向**（「太高」還是「太低」）。寫成「不符合這一
檔」的話，一個帶 40C 的人會往下改，然後更不合法。

### 5b. 房名是系統取的

玩家取不到房名。組法是「規則名 + 檔位」，**`[COST:n]` 那一段永遠完整**，被截的
只會是前面的規則名：

```
   夾擠式罰C [COST:57]
   └─ 規則名 ─┘└ 檔位 ┘        ← 對照官方的 Quickmatch [COST:57]
```

房名的功能是讓大廳裡的人一眼看出「這是哪一檔」—— 那正是亞城的房間列在做的事，
而自動配對要取代它。讓玩家自己取的話那個資訊就沒了。

⚠ 上限是 20 個字。那是**插件自己的**上限，不是實測出來的伺服器上限 —— 依據是
官方快速比賽開出來的房名剛好 20 個字，所以 20 一定塞得下。

**為什麼是規則「名稱」而不是規則族？** 規則族（`tomorin/squeeze-band`）本身就
20 個字，跟 `[COST:57]` 併不進同一個房名；截成 `squeeze-ba` 之後既不好讀、也
不再是識別碼，兩邊都沒了。而房名**本來就不是識別碼** —— 決定誰配得到誰的是
配對鍵（裡面放的正是規則族），那個玩家改不了也看不到，房名寫什麼都不會讓錯的
人配進來。既然它只是給大廳看的招牌，就該用玩家在「牌組 › Cost 表」看到的那個
名字，兩邊對照得起來。代價是同一族的不同版本可以改名字，所以大廳上可能出現
兩個標籤不同、卻排在同一條佇列的房 —— 那只影響觀感，不影響配對。

⚠ **房名絕對不能包含 token。** 房間清單是公開的，而 token 就是房間密碼。

### 官方的 COST 檔位只是快速鍵

自訂 COST 想約幾就填幾 —— 但**平常對戰最常約的就是官方那幾檔**（`[57,66,78]`），
所以配對頁把它們列成按鈕，省得每次自己打數字。按下去填的是**那一檔的上限**，
實際收的區間由上面那條規則決定（57 → 56.01～57.00）。

⚠ **duel 頻道自己沒有檔位。** 2026-08-16 兩個客戶端實測（59222 迪特、9334 亞城）：

```
channels       = {"1":{type:"ranked",cost:[57,66,78]}, "2":{type:"duel"}}
channels_cross = {"3":{type:"ranked",cost:[56,69,71]}, "4":{type:"duel"}}
```

2 與 4 **連 `cost` 這個鍵都沒有**。玩家給的規則是「頻道二用亞歷山卓城的、頻道四
用峰亥盧遺跡的」，而實測的結構比那個對映更基本：`channels` 與 `channels_cross`
是**兩組各自成套**的頻道（各走一條 socket），每組裡一個 ranked 一個 duel，
duel 借同組 ranked 的。`costTiersFor()` 照這個結構推導。

⚠ **不要寫死成 `{2:1, 4:3}`。** 官方哪天多開一組頻道，寫死的版本會安靜地拿到
另一組的數字 —— 而 1 是 `[57,66,78]`、3 是 `[56,69,71]`，**兩組真的不一樣**，
拿錯不報錯，只會讓兩個人約定到不同的上限然後配不到彼此。

⚠⚠ **這些數字每週二遊戲更新會跟著變**，所以插件每次都從玩家自己的客戶端現讀，
不快取、不寫進設定檔、更不烤進程式碼。存起來的症狀是「明明兩個人都按了 57
卻永遠配不到」—— 一邊用上週的、一邊用這週的，算出不同的配對鍵。

## 5c. 頻道要看三次

房間清單是**分頻道推播**的，所以「兩個人都在同一個頻道」不是設定問題，是這件事
成不成立的前提。頻道因此進配對鍵，而且要檢查三次：

| 什麼時候             | 檢查什麼                                             |
| -------------------- | ---------------------------------------------------- |
| 按下「開始自動配對」 | 玩家在頻道裡嗎（沒有的話直接說「請先進入一個頻道」） |
| **排隊中，每 5 秒**  | 玩家**還**在那個頻道嗎（不在就自己停）               |
| **每次配到人**       | 同上，最後一道                                       |

後兩次都不能省，而且不是同一件事。**每 5 秒那一次**是收尾路徑（見上面「排隊
途中玩家跑掉了怎麼辦」）：它讓佇列連線不會在玩家去打別場時繼續掛著。**配到人
那一次**是最後一道閘，擋的是那 5 秒之間切走的窗口 —— 少了它的症狀分兩種，兩種
都很難懂：host 會在新頻道開一間房（對手在舊頻道根本看不到它），guest 會在新
頻道的清單裡找一個不存在的 room_id 找到逾時。

## 6. 判斷在客戶端，為什麼這仍然是安全的

換成語義驗算之後，判斷從「物理上碰不到」變成了客戶端自己算。改過的插件可以
跳過驗算嗎？可以，但**沒有用**：

- 開房的是 host、進房的是 guest，**兩邊都得各自走完自己那半段**
- 對手的插件會獨立算一次，算不過就不會進來

所以要繞過去必須**兩邊都改過**，而那時他們本來就是講好的 —— 兩個講好的人從來
就可以不裝插件直接開房。這跟準備／秒數協商是同一條原則：**會改變勝負的東西
一律要雙方都同意才生效**。

## 7. 對手的牌組不會出現在畫面上

跨版本驗算要交換牌組描述子，所以插件**知道**對手帶了哪三隻。它只拿去算指紋，
然後就丟掉：

- 不放進 `PairingStatus`（UI 唯一看得到的東西）
- 不寫進記錄檔
- 沒有任何介面問得到它

這不是隱藏資訊的問題 —— 房間清單本來就把雙方牌組（含 `chara`、`charaIndex`、
`cost`）廣播給大廳裡**每一個人**，MatchingLobby 的房間列確實會畫出雙方的卡片
縮圖。這是**運動精神**的問題：看得到對手帶什麼就能挑對手，而那會讓整個約戰
功能失去意義。

⚠ 同一份規則的配對（絕大多數）根本不會走到交換那一步 —— `EXACT` 快路存在的
理由一半是效能，一半是這個。

### 中間人看得到什麼

誠實地列：

| 東西               | 中間人看得到嗎                                                           |
| ------------------ | ------------------------------------------------------------------------ |
| 配對鍵             | ✅ 但它是雜湊，看不出是哪份規則                                          |
| 規則標籤           | ✅ 同上，而且拌了配對鍵，換一條佇列就是另一個字串                        |
| 牌組描述子         | ⚠ **它經手**（`q-deck` 的 `body`）。它不解讀，但那是設計選擇不是數學保證 |
| 玩家身分、房號原文 | ❌ 從來不上去                                                            |

⚠ **這裡跟房號那條的保證強度不一樣，不要混為一談。** 房號是雜湊過的，
「中間人認不出那是哪一場」是數學問題；牌組描述子是明文轉發的，「中間人不看」
是它的行為。要更強的保證只有兩條路：端對端加密（雙方沒有共同祕密可以派生，
token 是中間人自己產的），或是由一台**保存所有規則版本**的伺服器代算
（那是 ULGG 的角色，WP-03 之後才可能）。

現階段的取捨是：**跨版本相容只在 `EXACT` 不成立時才交換，而交換的內容在幾秒後
就會由遊戲自己公開廣播給整個大廳。**

## 8. 還沒做的

- **武器與事件卡不在描述子裡。** 它們的正規鍵還沒定案
  （[open-questions.md](open-questions.md) 第 1 題：`entityId` 仍是寬鬆的
  pattern）。把還沒定案的東西寫進描述子，會讓兩個版本的插件對同一副牌算出
  不同的鍵 —— 症狀是「規則明明一樣卻說不相容」。定案之後加欄位並把
  `EVALUATION_FORMAT_VERSION` 加一。
- **戰果不會標記相容性。** 跨版本打完的那一場應該記成 `1.5.0 × 1.5.1` 而不是
  塞進其中一版，否則 Character Analysis 的版本統計會失真。那是 WP-05／WP-06
  的事（ULGG 端）。
- **本機 broker 沒有佇列。** 玩家把中間人設成 `local` 時自動配對連不上 ——
  那個組合是雙開測試用的，`broker.ts` 只認得房間協定。
- **牌組是配對當下讀的。** 玩家在「驗算完」到「房開好」之間換牌組的話，實際
  打的會是新的那副。這個窗口關不掉（送出開房封包的是遊戲自己），但它需要
  玩家刻意在幾秒內操作。
