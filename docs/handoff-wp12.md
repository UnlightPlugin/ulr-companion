# 交接：WP-12 移動階段仲裁（2026-08-03）

核心三層在 08-02 寫完，08-03 修掉一個玩家回報的 bug，並把**整個生命週期**
補齊 —— 現在它是「開著它去玩」的東西，不是「進對戰之後才啟動」的東西。

## 現在能跑的東西

給人用的入口（會自己找客戶端，錯誤不會一閃而過）：

```powershell
.\tools\arbiter.ps1                # 網頁版 :9334（預設）
.\tools\arbiter.ps1 -Port 9333     # 桌面版
```

雙擊 `tools\arbiter.cmd` 也可以 —— 它會 `pause`，視窗不會帶著錯誤訊息消失。

底下實際跑的是：

```powershell
npx tsx apps/companion/src/index.ts arbiter --port 9334 --policy either --deadline 3
```

`npm run verify` → **286 綠**。

**遊戲不必先開。** 連不上就等，還在大廳也裝得上，對戰中途接手也行，
打完重新開房會自己重掛。Ctrl+C 會把攔截拆乾淨。

```
頁面 patch-ok.ts  ──回報──▶  arbiter-runner.ts  ──▶  arbitration.ts
     ▲             ◀─心跳─    （翻譯與排序）        （純函式規則）
     └────── release / cancel / 改外觀 ◀────────────────┘
```

| 檔案                                                               | 跑在哪 | 職責                                 |
| ------------------------------------------------------------------ | ------ | ------------------------------------ |
| [arbitration.ts](../packages/cdp-adapter/src/arbitration.ts)       | Node   | **規則**：取消策略、雙方就緒、硬底線 |
| [arbiter-runner.ts](../packages/cdp-adapter/src/arbiter-runner.ts) | Node   | **只有翻譯與排序**，沒有規則         |

中間那層刻意不做決定 —— 一旦它也開始判斷，同一份邏輯會散在三個地方。

## 08-03 修的兩件事，成因是同一個

玩家回報三個症狀，**看起來是三個 bug，其實是兩個，而且都不在仲裁邏輯裡**：

| 玩家看到的                       | 真正的原因                          |
| -------------------------------- | ----------------------------------- |
| 剩 5 秒內按 OK，滑鼠移開就取消了 | `release()` 拆了 pin 但沒設終態     |
| 剩 10 秒內出牌不會取消準備       | 換房後 `onAny` 死了（或已 commit）  |
| 現在完全無法取消準備             | companion 沒在跑，孤兒 patch 還在攔 |

共通點：**插件失效的方式是「單向的鎖」** —— 壓住 OK 的那一半活著、解除它的
那一半死了。三個症狀全部長這樣。

### 1. `release()` 只做了一半

拆掉 pin 之後遊戲自己的 hover handler 回來了，而按鈕還停在 frame 2 且仍然
`setInteractive()`。滑鼠一移開 → `pointerout` → frame 0 → **看起來像準備被
取消，其實 `I_am_ok` 早就送出去了**；而且還能按，再按一次會攔到第二個。

終態必須是 frame 2 **且不可按**（＝遊戲原本按完 OK 的樣子）。
階段已結束時例外 —— 那顆鈕已經屬於下一階段，碰它會鎖死在攻防階段。

### 2. 失敗模式的方向反了

原本是「先攔住，Node 沒反應就靠 25 秒失效保護兜底」。Node 死了就變成
每個移動階段罰玩家 25 秒，而且取消不了。

現在 Node 每個 tick 都送心跳，**超過 3 秒沒心跳頁面就停止攔截**、放掉正壓著
的呼叫、把琥珀色收回去。不攔只是功能沒生效；攔了沒人管是實質傷害。

## 生命週期：四種時機都要成立

| 時機         | 靠什麼                                               |
| ------------ | ---------------------------------------------------- |
| 遊戲還沒開   | `connectWhenReady()` 無限重試，不放棄                |
| 開了還在大廳 | 裝得上去、回 `waiting`，`phaseTick` 自己補掛         |
| 對戰中途接手 | `Runtime.evaluate` 注入，不需要 reload               |
| 打完重新開房 | `arm()` 偵測 socket 換了 → 重掛 + `ok-patch-rearmed` |
| Ctrl+C       | `uninstallOkPatch()`，先送出壓著的再還原 emit        |

**重新開房那條是 08-03 才發現的**：`MainA.socket` 借自 `MatchBoot`，而
`MatchBoot` 每次進配對就 `new WSClient(...)`。原型上的 patch 跨場活著，
實例上的 `onAny` 不會 —— 原始碼證據見
[battle-events.md](battle-events.md) 的「socket 的壽命」。

---

## 這個功能有七個「會完全失效」的坑

全部有測試釘住，細節在 [battle-features.md](battle-features.md)。

1. 遊戲按下 OK 後 `disableInteractive()` → frame 與可按狀態要分開設
2. 第二次按 OK 不能直接放行 → 否則永遠取消不了
3. 遊戲的 hover handler 會蓋掉我們設的 frame → 把它**暫時收起來**
4. **`release()` 要設終態，不是只拆 pin** → 否則滑鼠移開就假裝成「取消了」
5. 送出後沒重置 → `committed` 卡 true，整場剩下的階段全部不再仲裁
6. **座位不能快取** → 換房後敵我反了
7. **socket 每場換一顆** → 只 patch 原型的話換房後出牌不再取消準備

### 犯過兩次的錯：熱更新只換設定，不換程式碼

`ws-events` 的取值模式與 `patch-ok` 的 pin 都栽在這裡。症狀一模一樣：
**測試綠、實跑沒反應**，而且很容易誤判成邏輯寫錯，去改本來正確的程式碼。

判斷方式：查一個新版才有的副作用（listener 數量、新欄位），不要查行為對不對。

`installOkPatch()` 會先拆再裝；`installWsWatch()` 仍只換設定（改邏輯要重載遊戲）。

### 測試：字串比對不夠

坑 #4 與心跳**都會通過字串比對**。`patch-ok.test.ts` 現在有一組用 `node:vm`
把注入腳本真的跑起來的測試，假的只有 Phaser 與 WSClient 的行為（frame、
hover、原型共用、`onAny` 掛實例）。

> ⚠ vm context 有**自己的 `Date`**，vitest 的假時鐘只換主 realm 那顆。
> 不把外面的 `Date` 傳進 sandbox，心跳永遠不會過期，測試會綠得毫無意義。

## 視覺語意（玩家定的，不要自己改回去）

**顏色代表階段，frame 代表狀態。**

|                   | OK 鈕                  |
| ----------------- | ---------------------- |
| 移動階段（整段）  | **琥珀色**             |
| 移動階段 · 準備   | 琥珀色**鎖頭**，仍可按 |
| 移動階段 · 已送出 | 琥珀色鎖頭，**不可按** |
| 攻擊／防禦        | 白色，完全原本的行為   |

早期版本把染色綁在「準備中」上，取消後變回白色 —— 同一階段內顏色自己打架。
玩家指出後改成階段驅動，**這是刻意的設計決定**。

染色現在還多一個條件：**Node 活著且攔截真的掛著**。畫面不該宣稱一個已經不
存在的保護 —— 琥珀色消失就是「插件現在沒在管」的可見訊號。

## 三個不變量（不能為了方便而妥協）

1. **本機硬底線優先於仲裁結果。** 不管對方說什麼，`okInvisibleA` 之前一定要
   送出 `I_am_ok` —— 壓著不送 = 棄權，而且是我們造成的。
2. **側通道只傳合成訊號。** 只發「雙方都好了」，**從不**單獨告訴任何一方
   「對手準備好了」。這保住了「伺服器從不下發對手 OK 狀態」的性質 ——
   它現在從協定保證降級成我們的設計選擇，所以必須有測試釘住。
3. **重放原始參數。** 攔到的呼叫原封不動送出，插件永遠不需要知道它的協定。
