# 預先出牌：能不能不等伺服器解鎖就先出牌（2026-08-06 雙邊實測）

玩家問的是：「移動階段收到事件卡後就開放操作、記在本地，等伺服器解鎖再一次
送出，可以嗎？攻擊、防禦階段也是。防禦方要看到攻擊方出了哪些牌，是不是要靠
中間人轉送？」

**結論：可以，而且中間人一個位元都不需要傳。** 防禦方要的資訊遊戲本來就提早
給了 —— 這一點跟直覺相反，而且它推翻了本文件作者自己在同一次討論裡先講過的
判斷。

[battle-timing.md](battle-timing.md) 的結論是「客戶端幾乎沒有槓桿」。那句話對
**動畫**成立，對**預先出牌**不成立 —— 兩者攻擊的是不同的東西：動畫加速搶的是
決策窗裡被擋住的 11.3 秒，預先出牌搶的是決策時間本身。

---

## 最重要的一條：**攻擊與防禦是循序的，不是同時的**

`endPhase` 帶著下一個階段名，而**兩個座位收到的值不同**（949.js）：

```js
case "attack":  t.scene.start("AttackPhaseA");
case "defense": t.scene.start("DefensePhaseA");
```

一開始看到這段，加上實測同一時刻一邊在 `AttackPhaseA`、另一邊在
`DefensePhaseA`，很容易推論成「攻防同時進行」。**那是錯的**，而且錯得很有說服力
—— 兩個場景確實同時 active，但**可操作的只有其中一邊**。

雙邊錄的時間軸（座位 A 側）：

```
我當攻擊方
138.40  場景 → AttackPhaseA
138.64  playerAtkA 0 / playerDefB 3 / okVisibleA / cardController1A   ← 我解鎖
138.76…139.76  我出 4 張牌
140.38  →I_am_ok
140.42  cardController2A / cardOpen_A        ← 我一承諾，我這半段立刻結束
142.22  timerReset                            ← 防禦方的窗才開始

我當防禦方
156.30  場景 → DefensePhaseA                 ← 場景換了，但我不能動
157.40  ←cardclickedB 2 T                     ← 攻擊方出第一張，我看到背面
157.74  ←cardclickedB 1 T                     ← 第二張
158.87  ←cardOpen_B  /  playerAtkB 11         ← ⭐ 正面攤開 ＋ 攻擊值
160.27  timerReset / defensePhaseA / cardController1A
160.40  手牌解鎖                              ← 我到這裡才能動
```

**判斷階段狀態要看 `cardController1X` / `cardController2X`，不要看場景名。**
場景先換、可操作性後到，中間那 1.5~3.7 秒正是預先出牌的機會窗。

### 直接後果：防禦方要的資訊，遊戲提早 1.5 秒就給了

| 玩家想要的           | 實際來源                        | 什麼時候 |
| -------------------- | ------------------------------- | -------- |
| 看到攻方牌的**背面** | `cardclicked<對手>`（即時廣播） | 出牌當下 |
| 知道攻方**結束出牌** | `cardOpen_<對手>`               | 解鎖前   |
| 看到攻方牌的**正面** | `cardOpen_<對手>` 就是正面      | 解鎖前   |
| 知道攻擊值           | `playerAtk<對手>`               | 同上     |

實測 8 個防禦窗，`cardOpen_<對手>` → 解鎖 全部落在 **1.55~3.69 秒**。

**所以「中間人把攻方的牌傳給防方」整條可以砍掉。** 這不只是省工 ——
ulgg 轉送對手狀態會踩到 [battle-features.md](battle-features.md) 的不變量 2
（側通道只傳合成訊號），而現在根本不需要為它破例。

> ⚠ 但**「攻擊方按了 OK 就給防禦方看正面」如果指的是比 `cardOpen_` 更早**，
> 那仍然是洩密，而且它會自我毀滅：一旦「先按 OK ＝ 把手牌交出去」，理性玩家
> 就永遠不先按。速度一秒沒省，還多了一個策略陷阱 —— 正是 WP-12 要消除的
> 那個「先承諾的人被懲罰」，換個更貴的形式重新引入。

## 第二條：`max(A,B)` **只適用於移動階段**

[battle-timing.md](battle-timing.md) 寫「階段是雙方都按才結束，階段長度是
`max(A,B)` 不是 A」。**那句話只對移動階段成立。**

移動階段（同時承諾），實測 4 組全部符合，誤差 <0.1s：

```
 22.5s  :59222 5.50s  :1221 6.26s   階段長 6.34s
 77.5s  :59222 2.13s  :1221 3.32s   階段長 3.45s
163.3s  :59222 0.26s  :1221 1.01s   階段長 1.09s
212.3s  :59222 3.26s  :1221 1.43s   階段長 3.40s
```

攻擊／防禦階段（循序），`I_am_ok` → `cardController2` **15 次全部在 41~44ms**
（:1221 的防禦側 106~193ms，仍然遠小於任何等待）：

```
:59222  攻擊 42/41/43/44/44ms   防禦 41/42/42/42ms
:1221  攻擊 43/43/49/42ms      防禦 106/183/173/193ms
```

**你一承諾，你那半段就結束，完全不等對手。**

### 所以攻防階段的預先出牌**單邊就直接省到時間**

這是整份文件對排程最重要的一句。移動階段要雙邊（要 ulgg／WP-12 握手），
攻防階段不用 —— 對手有沒有插件都一樣。

## 機制：出牌是伺服器回音驅動的，而重繪函式是冪等的

點手牌時客戶端只做兩件事（828.js:906）：

```js
i[0].on("pointerdown", () => { … e.socket.emit("card", e.room, e.id, t), i[0].disableInteractive(); });
```

**畫面完全不動。** 牌要等伺服器廣播 `cardclicked<座位>` 回來、觸發
`player_card_clicked()` 才會飛到 y=380（949.js:1465 的繫結）。

所以預先出牌不能只是「攔住 emit」—— 那樣玩家點下去會什麼都沒發生。必須自己
把牌演出來。而這件事之所以安全，是因為 `player_card_clicked` **不是 toggle，
是從目前 y 座標重算版面**：

```js
for (const n of this.arr1) null !== n && n[0].disableInteractive();   // ① 整手牌鎖住
let i = arr1.flatMap((t, s) => 510 === t[0].y && s != e ? s : []),   // 手牌
    a = arr1.flatMap((t, s) => 380 === t[0].y && s != e ? s : []);   // 已出
!0 === t ? a.push(e) : i.push(e);
… tween 100ms …  await 110ms  …                                      // ② 強制空窗
for (…) if (!1 === s) this.arr1[n][0].setInteractive();              // ③ 解鎖
```

### ✅ 實測驗過：本地演出可行，而且冪等

不碰伺服器，直接呼叫 `player_card_clicked(0, true, false)`：

```
原始        手牌[0 1 2 3 4 5 6]   已出[]
預測 60ms   0(y409-) ← tween 中，全手牌被鎖（②）
預測 360ms  手牌[1 2 3 4 5 6]     已出[0(y380+)]
回音重放後   手牌[1 2 3 4 5 6]     已出[0(y380+)]   ← 一模一樣
收回後      手牌[0 1 2 3 4 5 6]   已出[]
漏出去的封包：（無）
```

**同一組參數跑兩次結果完全相同**，所以本地先演一次、伺服器回音回來再演一次，
版面不會壞。這是整個功能的地基 —— 沒有它就得自己維護一份影子狀態，
而那是 desync 的溫床。

### 每出一張牌被強制卡 154ms

上面的 ①→③ 是真實成本，而且**發生在決策窗裡面**：

```
138.76 →card       138.80 ←回音（RTT 44ms）
138.90 手牌全鎖    139.01 解鎖（+110ms）
```

| 量到的     | 值                     | 樣本       |
| ---------- | ---------------------- | ---------- |
| RTT        | 中位 **44ms**（41~47） | 23 + 13 次 |
| 出牌後鎖住 | 中位 **102ms** / 101ms | 20 + 18 次 |

⚠ 那個 110ms 是 `scene.time.addEvent`，**`patch-speed` 舊版結構上碰不到它**
（它只動 tweens）。現在動得到了，見下面「兩顆 Clock」。

## 量到的預算與決策時間

「預算」＝ 決策所需資訊全部到齊 → 手牌解鎖，中間那段死時間。

| 階段 | 錨點（資訊到齊）  | 預算中位  | 預算最短 | 決策中位 | 預算 ≥ 決策 |
| ---- | ----------------- | --------- | -------- | -------- | ----------- |
| 移動 | `drawPhase`       | 3.66s     | 2.97s    | 3.26s    | 7/10        |
| 攻擊 | `goToBochi`       | **2.68s** | 2.64s    | 2.39s    | 6/9         |
| 防禦 | `cardOpen_<對手>` | 1.94s     | 1.55s    | 1.21s    | 6/8         |

**三個階段的預算都略大於決策中位數** —— 預先出牌吃得下大部分，但不是全部。

### ⚠ 錨點選錯會低估兩成以上

攻擊階段一開始用 `endMovePhase` 當錨點，算出 1.68s。但手牌其實是
`goToBochi`（移動牌進墓地）才定案，正確答案是 **2.68s**。差別足以把
「預算不夠、要另外想辦法」翻成「預算夠」。

錨點的判準是「**在這之前玩家不可能做決定**」，不是「階段開始」。

### ⚠ 防禦階段的決策時間會被「沒出牌」的窗污染

8 個防禦窗裡有 4 次玩家一張防禦卡都沒出，決策時間 ≤0.12s。把它們混進中位數
會算出 0.12s，然後得到「防禦階段沒東西可省、不值得做」的**錯誤結論**。

```
有出防禦牌 4 次   1.21s / 1.36s / 1.85s / 2.33s   ← 跟攻擊階段同一個量級
沒出防禦牌 4 次   0.00s / 0.09s / 0.10s / 0.12s
```

而防禦階段的預算（1.55~1.94s）是三者中最緊的 —— 它不是最不需要做的，是**最
需要把預算擠出來的那一個**。

### 收益估計

| 手段                | 每場約 | 需要對手？ |
| ------------------- | ------ | ---------- |
| 攻擊階段預先出牌    | 17s    | 否         |
| 防禦階段預先出牌    | 7s     | 否         |
| 移動階段預先出牌    | 22s    | **是**     |
| （對照）動畫加速 ×3 | 7.5s   | 否         |

⚠ **這是外推，不是實測。** 用「每階段 min(預算, 決策)」乘上
[battle-timing.md](battle-timing.md) 的 28 個階段推的，而樣本只有兩場、
一位玩家。單邊約 3 倍於動畫加速，雙邊約 6 倍 —— **不是一個數量級**
（本文件作者一度這樣講過，是高估）。

## 亮牌：200ms × N，而且沒有任何動畫

玩家回報「看對方的牌一張一張慢慢亮很煩躁」。原始碼
（`./src/helper/battle/CardOpen.ts`，webpack 保留了原始路徑）：

```js
async showcards(scene) {
  for (let i = 0; i < this.array.length; i++) {
    this.array[i].card === 'locked' ? scene._ulse28.play() : scene._ulse29.play();
    scene.card2[this.array[i].cardindex][0].setVisible(false).destroy();
    this.card[i].forEach((element) => { element.setVisible(true); });   // ← 瞬間完成
    scene.card2[this.array[i].cardindex] = this.card[i];
    await new Promise((resolve) => {
      scene.time.addEvent({ delay: 200, callback: () => { resolve(); } });   // ← 慢的是這個
    });
  }
}
```

三件事：

1. **不是動畫。** 亮牌是 `setVisible(true)`，慢的 100% 是那個 `delay: 200`。
2. **`cardOpen_X` 的封包一次就把整組牌送來了**（`array` 是完整的）。一張一張亮
   **不揭露任何新資訊**，只是把已經在本機的資料慢慢演給玩家看。
3. 它掛在 `scene.time` 上，`scene` 是 MainA。

### ⚠ 加快它**不會讓對戰變短**

亮牌發生在伺服器空檔裡，而且 `card_open_*` 會 `timer.paused = true`（171.js）。
伺服器排程紋風不動（battle-timing.md 的受控實驗）。它的價值是另外兩個：

- **治煩躁**（這本來就是獨立的價值）
- **把預先出牌的可用預算還回來** —— 防禦階段預算只有 1.94s，攻方出 4 張牌
  光亮牌就吃掉 800ms

第二點才是關鍵：它讓防禦階段從「預算勉強夠」變成「夠」。

> 順帶：發牌動畫是 `delay: 360 * t, duration: 250`（949.js:1633），五張牌
> 1.69 秒 —— 但 `drawPhase` 的封包在第一格動畫開始前就把**整手牌**交給客戶端
> 了。玩家問的「發牌期間就能出已經發的牌」不只成立，整手牌從第 0 毫秒就已知。

## 兩顆 Clock：MainA 的可以動，階段場景的不行

2026-08-06 實測確認 `MainA.time` 與 `MovePhaseA.time` 是**不同的 Clock 物件**，
各自有獨立的 `_active` 與 `timeScale`。這是 `patch-speed.ts` 能加速亮牌的
全部依據。

| Clock            | 上面有什麼                                       | 能不能加速 |
| ---------------- | ------------------------------------------------ | ---------- |
| `MainA.time`     | 亮牌 `delay:200`、出牌 `await 110ms`、音效、提示 | ✅         |
| 階段場景 `.time` | **倒數**（`delay:100` + `repeat:300`，171.js）   | ⛔         |

加速階段場景的 Clock 有兩個後果，第二個更嚴重：玩家看到假的剩餘秒數；
**WP-12 仲裁讀那個 TIME 算硬底線**，倒數跑快 N 倍 → 硬底線提早 N 倍觸發 →
`I_am_ok` 被提早送出。

佐證加速 MainA 是安全的：949.js 裡 15 處 `time.addEvent` 全是一次性的
（delay 30~4400ms），**一個 `repeat` / `loop` 都沒有** —— 那顆 Clock 上沒有任何
「跟時間有語意關係」的東西，不需要像循環 tween 那樣補償。

⚠ 名單用**白名單**（`REVEAL_CLOCK_SCENES`）不是黑名單。遊戲以後新增階段場景，
黑名單會漏，而漏掉的後果是玩家棄權；白名單頂多是少加速一個場景。

⚠ 比對要**完全相符**。實測大廳裡 `MainAAssets` 是 active 場景 ——
任何「包含 Main」之類的模糊比對都會把它一起吃進去。

## 還沒解的三件事

### 1. ⬜ 伺服器收不收「一口氣送 N 張牌」

**這是整個功能最大的未知。** 真實客戶端每張牌之間一定隔著一個 RTT
（被 `disableInteractive()` 鎖著），所以 flush 的爆量是伺服器從沒見過的形狀。
它要是只收第一張、其餘丟掉，玩家整個階段就只出得了一張牌。

做法：正常解鎖窗裡用 CDP 在同一個 tick emit 三次 `card`，數回來幾個
`cardclicked`。出牌是可逆的（再送一次同一個 index 就是收牌），所以測起來安全，
但要檢查 TIME 餘裕、測完自動收回、收不回來要大聲報錯。

### 2. ⬜ 亮牌的 200ms 沒有線上實測

只有原始碼證據（鏡像是 2026-07-29 的 dev build）。`player_card_clicked` 有做過
一字不差的線上比對，`CardOpen` 沒有。

> ⚠ **第一次嘗試測它拿到 0 個樣本**，原因是探針把 `onAny` 掛在 socket
> **實例**上而沒寫重掛 —— 正是 [battle-events.md](battle-events.md)
> 「socket 的壽命」那一節。打完一場換新 socket 就聾了。
> **任何要跨場活著的探針都必須自己 `arm()`。**

### 3. ⬜ desync 的對帳策略

flush 之後每張牌都要等到自己的 `cardclicked` 回音才算數。沒等到就本地
`player_card_clicked(i, false, false)` 收回來並明確報錯。

**玩家以為出了牌其實沒出，比功能不生效嚴重得多** —— 跟 WP-12 的「單向的鎖」
是同一類失敗：測試全綠、邏輯也對，但玩家輸掉對局。

## 建議順序

1. **亮牌加速**（已實作，`patch-speed.ts` 的 `REVEAL_CLOCK_SCENES`）——
   純本地顯示、零公平性問題，而且它放大下面兩項的預算
2. **攻擊 + 防禦階段預先出牌** —— 單邊生效、共用同一套緩衝與對帳，先解 #1
3. **移動階段預先出牌** —— 要雙邊，跟 WP-12 的握手一起做
4. ~~中間人轉送~~ —— 不需要，資訊已經公開且提早送達

攔截的機制不用重寫：`patch-ok.ts` 那套（patch `WSClient.prototype.emit`、
原封不動重放、心跳、失效保護、`arm()` 重掛）就是要的東西，把 `I_am_ok`
換成 `card` / `rotate` / `move_select` 即可。三個不變量照舊 ——
尤其**本機硬底線優先**：壓著沒送出去就是棄權。

## 給下一個問「防禦方看不到攻擊方出什麼牌」的人

先確認你講的是哪一種：

- **看不到正面** → 遊戲有給，`cardOpen_<對手>`，比你能動早 1.5~3.7 秒
- **看不到背面** → 遊戲有給，`cardclicked<對手>` 即時廣播
- **亮得太慢** → `CardOpen.showcards` 的 200ms，已經可以加速
- **想在對方還沒 `cardOpen_` 之前就看到** → 那是洩密，而且會讓沒人肯先承諾

前三種都不需要中間人。第四種不該做。
