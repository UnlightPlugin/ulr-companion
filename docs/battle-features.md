# 戰鬥類四個功能的規劃

里程碑「戰鬥」底下的四項：移動階段仲裁、記未出現的手牌、紀錄牌譜、實況轉播。

這份只談這四項怎麼排、彼此靠什麼。**技術前提不在這裡重述** ——
`WSClient` 的可 patch 性、OK 鈕、倒數量法、對手 OK 狀態不外洩，全部在
[open-questions.md §4](open-questions.md) 有實測記錄，動手前先讀那節。

---

## 順序：牌譜要排在仲裁前面

使用者原本列的順序是「移動階段仲裁 → 記未出現的手牌 → 紀錄牌譜 → 實況轉播」。
建議倒過來做前三項，理由不是難易度，是**資料相依**：

移動階段仲裁的每一個門檻都需要真實分布，而現在的數字是憑感覺定的：

| 要定的數字                   | 目前的來源            | 需要什麼樣本                            |
| ---------------------------- | --------------------- | --------------------------------------- |
| 移動階段的 OK 視窗到底幾秒   | 只量過 3 次，都 31.0s | §4 訂的標準：每種階段 ≥3 次、全距 <1.5s |
| 「準備」窗口該多長           | 第一期拍板 3 秒       | 玩家實際決策時間的分布                  |
| 規則 3 的 25 秒門檻          | 憑感覺                | 出聖水時間點的分布                      |
| 備註的「15~30 秒」算不算拖條 | 憑感覺                | 同上，而且要看沒插件的人長什麼樣        |

牌譜記錄是**純觀測、不改遊戲行為**的，風險最低，而且它產出的就是上面那張表
缺的東西。先做它，仲裁的參數才有依據，而不是先寫死再回頭改。

「記未出現的手牌」是牌譜的一個推導 view，做完牌譜幾乎是免費的。
「實況轉播」轉播的內容就是牌譜流，也必須排在它後面。

於是：

```
WP-09  WS 事件層（地基，四項全部靠它）
  └─ WP-10  紀錄牌譜
       ├─ WP-11  記未出現的手牌
       ├─ WP-12  移動階段仲裁
       └─ WP-13  實況轉播
```

## WP-09：WS 事件層（地基）

`packages/cdp-adapter/src/index.ts` 的狀態列表裡，這項還是 ⬜。四個功能沒有它
一個都做不了，所以它是唯一真正擋路的東西。

要做的事：

1. **接收側**：`WSClient.onAny` 掛全域監聽。不必 patch，§4 已驗證。
2. **送出側**：換掉 `WSClient.prototype.emit`。原型未凍結、6 條連線共用同一份，
   patch 一次全包（§4）。
3. 兩側都透過既有的 `REPORT_BINDING_NAME` binding 回報到 Node 側，
   沿用 `patch-cost.ts` 的模式。

**去識別化在這一層做，不要留給呼叫端。** `DECK_EVENTS`（`db_deck1/2/3`）
送出時 `args[0]` 是 session token（constants.ts 有註記），§12 明訂不得記錄。
邊界擋一次，之後所有功能都安全。

> ⚠ 分析陷阱（§4 已踩過）：`meta.ACKs` 裡有事件名的字串參照，只看 `event`
> 欄位，不要 grep 整包 JSON。

## WP-10：紀錄牌譜

一場對戰的完整事件流，落地成可重播的檔案。

- 事件流本身就是牌譜 —— 不要自己維護一份遊戲狀態機，那會跟遊戲版本漂移。
  存原始事件 + 時間戳，需要什麼再從流推導出來。
- 時間戳要能算出 §4 要的區間：`okVisibleA` → `okInvisibleA`，
  而且**必須扣掉 `timerPause` → `timerResume` 的凍結時間**（機會三卡、聖水卡
  會凍結倒數，§4 有實測序列）。
- 隱藏資訊照收但不顯示、不落地：§12 明訂收到對手手牌也不得顯示或上傳。
  這條在牌譜功能上特別容易違反 —— 「完整記錄」的直覺跟它衝突。
- `.gitignore` 已經擋了 `**/battle/`、`**/deck/`、`packets.log`，牌譜要落在
  這些路徑底下。

順帶產出：`OK_WINDOW_SECONDS` 目前只有移動階段的 3 個樣本，這個功能會把
抽牌／攻擊／防禦三個階段的數字一起補齊。

## WP-11：記未出現的手牌

牌譜的推導 view：已知牌組（`db_deck*`）減掉場上出現過的，剩下的就是還沒出的。

唯一要小心的是**只能算我方**。對手牌組是隱藏資訊，§12 禁止使用 —— 就算封包裡
真的有也不行。UI 上要講清楚這是「我方未出牌」，不要讓玩家誤會插件在看對手的牌。

## WP-12：移動階段仲裁

最複雜的一項，而且是唯一會**改變遊戲行為**的。

### 先做 localhost，再接 ulgg

§4 已經指出：雙開讓第二期（雙邊）提前可做。現在雙開真的成立了
（桌面版 :9333 + 網頁版 :9334），所以第一個實作階段不需要蓋 ulgg：

1. 兩個插件用 localhost 串起來，把整套握手協定驗完
2. 協定不變，之後把傳輸層換成 ulgg 或 P2P

這樣 ulgg 的部署、認證、配對、濫用防治全部可以延後，而協定該有的性質
（同步釋放、不洩漏單邊狀態、本機硬底線）現在就能寫成測試。

### 實作結構（2026-08-02 完成核心層）

```
頁面 patch-ok.ts  ──回報──▶  arbiter-runner.ts  ──▶  arbitration.ts
     ▲                        （翻譯與排序）        （純函式規則）
     └────── release / cancel / 改外觀 ◀────────────────┘
```

| 檔案                | 跑在哪 | 職責                                       |
| ------------------- | ------ | ------------------------------------------ |
| `arbitration.ts`    | Node   | **規則**：取消策略、雙方就緒、硬底線       |
| `arbiter-runner.ts` | Node   | **只有翻譯與排序**，沒有規則               |
| `patch-ok.ts`       | 頁面   | 攔截、失效保護、原封不動重放、改 OK 鈕外觀 |

中間那層刻意不做決定 —— 一旦它也開始判斷，同一份邏輯會散在三個地方。

### ⚠ 失效保護必須在頁面裡

插件壓著 `I_am_ok` 的期間，如果 CDP 斷線、companion 當掉、Node 卡住，
玩家就**逾時棄權** —— 不可逆，而且是我們造成的。

所以頁面自己有一個 25 秒的計時器，完全失聯也會把攔到的呼叫送出去。
Node 的硬底線只是「比較早的那一道」，不是唯一的一道。

### 視覺語意：**顏色代表階段，frame 代表狀態**

|                   | OK 鈕                  | 意思             |
| ----------------- | ---------------------- | ---------------- |
| 移動階段（整段）  | **琥珀色**             | 插件有介入       |
| 移動階段 · 未按   | 琥珀色 OK              | 還沒準備         |
| 移動階段 · 準備   | 琥珀色**鎖頭**，仍可按 | 已準備，還能取消 |
| 移動階段 · 已送出 | 琥珀色鎖頭，不可按     | 不可逆           |
| 攻擊／防禦        | 白色，完全原本的行為   | 插件不碰         |

⚠ **早期版本把染色綁在「準備中」上** —— 結果取消之後變回白色 OK，
同一個階段裡按下去是琥珀、取消回來變白色，**顏色語意自己打架**，
玩家分不出那是階段標示還是狀態標示。玩家提出後改成階段驅動。

染色由一個一直在跑的階段監看維護，`setOkFrame` 不碰它。

### ⚠ 失敗模式的方向：**沒人管的時候要停手，不是繼續攔**

2026-08-03 之前的設計是「先攔住，Node 沒反應就靠 25 秒失效保護兜底」。
那在 Node 活著時是對的，Node 死了就變成**一把沒有鑰匙的鎖**：

- companion 一結束（Ctrl+C 就會），頁面上的 patch 原封不動留著
- 原型上的 patch 照樣攔 `I_am_ok`，但取消要 Node 下指令 —— 沒人下
- 玩家每個移動階段被壓滿 25 秒才送出，**而且按第二次也取消不了**

所以現在多了一道**心跳**：`ArbiterRunner` 每個 tick 都呼叫頁面的 `tick()`，
超過 `staleMs`（3 秒）沒收到，頁面就**停止攔截**、放掉正壓著的呼叫、把琥珀色
收回去。不攔只是功能沒生效；攔了沒人管是實質傷害。

失效保護退回它該有的位置：**最後一道，不是第一道**。看到 `failsafe` 代表連
心跳都沒發揮作用。

三件配套，缺一個就會留下孤兒：

| 做的事                             | 為什麼                             |
| ---------------------------------- | ---------------------------------- |
| `uninstallOkPatch()` 在結束前呼叫  | 不留孤兒（心跳只是讓孤兒不再傷人） |
| 頁面每 200ms 自己 `arm()`          | socket 換了要重掛，見下面坑 #7     |
| 沒 socket 也裝得起來（回 waiting） | 玩家的順序是「先開插件再開遊戲」   |

### 七個會讓功能完全失效的坑（全部實測踩過）

前四個是實作時想到的，後三個是**在真實對戰裡才浮出來的**——
單元測試全綠、邏輯也對，但跑起來就是沒反應。

1. **遊戲按下 OK 後會 `disableInteractive()`。** frame 與可按狀態必須分開設，
   否則「再按一次取消」根本按不到。
2. **第二次按 OK 不能直接放行。** 直覺會寫「已經壓著就直接送出」，那樣玩家
   永遠取消不了，等於功能不存在。
3. **遊戲的 hover handler 會蓋掉我們設的 frame。** 因為要保持可按，滑鼠一移開
   就被改回普通 OK。解法是**把遊戲的 hover handler 暫時收起來**，不是再掛一組
   去搶 —— 搶的版本漏拆時會讓「滑過去」直接顯示成準備狀態，玩家根本沒按。
4. **`release()` 必須自己收拾外觀，而且「拆 pin」只做了一半。** 失效保護那條路
   完全沒有 Node，而硬底線那條路 `step()` 只回 `send-ok` 不回 `set-ok-frame`
   —— `commandsFor()` 裡那個 `interactive: false` 永遠輪不到。
   ⚠ **只呼叫 `pinFrame(null)` 不夠**（2026-08-03 玩家回報）：遊戲的 hover
   handler 回來了，而按鈕還停在 frame 2 且仍然可按，於是**滑鼠一移開就變回
   frame 0，看起來像準備被取消**，其實 `I_am_ok` 早就送出去了；而且還能再按
   一次，攔到第二個 `I_am_ok`。送出後的終態必須是 frame 2 **且不可按** ——
   那正好是遊戲原本按完 OK 的樣子，所以下個階段遊戲會自己還原。
   （階段已結束時例外：那顆鈕已經屬於下一階段，碰它會鎖死在攻防階段。）
5. **送出後沒有重置 → `committed` 卡在 true**，整場剩下的階段全部不再仲裁，
   **而且完全沒有錯誤訊息**。runner 收到 `ok-released` 就重置。
6. **座位不能快取。** 每場重新分配，實測同兩個帳號連打兩場會對調。用舊座位的
   症狀是「對手動作不取消準備、自己動作反而取消」——完全不像座位問題。
   現在每次 `ok-intercepted` 都重讀。
7. **socket 每場換一顆，`onAny` 掛在實例上。** 只 patch 原型的話，重新開房
   之後攔截照常、但出牌／轉牌不再回報 → **取消準備永遠不會觸發**，又一把
   單向的鎖。症狀是「出牌不會取消準備」，看起來像仲裁邏輯錯，其實邏輯沒錯。
   細節與原始碼證據見 [battle-events.md](battle-events.md) 的「socket 的壽命」。
   現在 `phaseTick` 每 200ms 自己 `arm()`，換了就 `offAny` 舊的、重掛新的，
   並回報 `ok-patch-rearmed` 讓 Node 把座位與場上牌組整組丟掉。

全部有測試釘住，而且 `patch-ok` 現在**有一組真的把注入腳本跑起來的測試**
（`node:vm` + 假的 Phaser／WSClient）。坑 #4 與心跳都會通過字串比對，
只有把它跑起來才抓得到。

> ⚠ 寫那組測試時踩到的：**vm context 有自己的 `Date`**，vitest 的假時鐘只換掉
> 主 realm 的那顆。不把外面的 `Date` 傳進 sandbox，腳本裡讀到的是真實時間 ——
> 心跳永遠不會過期，測試會綠得毫無意義。

### 兩次犯同一個錯：熱更新只換設定，不換程式碼

`ws-events` 的取值模式與 `patch-ok` 的 pin 都栽在這裡。症狀一模一樣：
**測試全綠、實際跑起來沒反應**，而且很容易誤判成邏輯寫錯，去改本來正確的程式碼。

`installOkPatch()` 現在會先拆再裝，拆的順序有講究：

1. 先把壓著的呼叫送出去（`by: "reinstall"`）—— 半路丟掉會害玩家棄權
2. 還原 `emit`，否則新 patch 包在舊的外面變成兩層攔截
3. 拆掉 hover 收納與染色，不留孤兒

`installWsWatch()` 還是只換設定，限制寫在它的註解裡。

### 送出的原因，看到 `failsafe` 就要查

| `by`                      | 意思                                     |
| ------------------------- | ---------------------------------------- |
| `arbiter`                 | 正常路徑                                 |
| `phase-ended`             | 階段結束，壓著已無意義（頁面自己判斷）   |
| `node-gone`               | 心跳過期（3 秒），不等 Node 了           |
| `failsafe`                | 壓滿 25 秒 —— **代表連心跳都沒發揮作用** |
| `reinstall` / `uninstall` | 換版或拆掉前先送出                       |

⚠ 2026-08-02 的實測裡**每一次都是 `failsafe`**，也就是 Node 的硬底線從來
沒觸發過。原因是 `#tick()` 的錯誤變成無人處理的 promise rejection 被靜默
吞掉。現在有 `onError`，讀不到 TIME 會直接印出來。

### 三個一定要守的不變量

1. **本機硬底線優先於仲裁結果。** 不管 ulgg／對方插件說什麼，
   在 `okInvisibleA` 之前一定要送出 `I_am_ok`。§4 Q1 已證實時間到伺服器
   自己會結束回合，但插件壓著不送 = 棄權。
2. **側通道只傳合成訊號。** ulgg 只發「雙方都好了 → 鎖」，
   **從不**單獨告訴任何一方「對手準備好了」。這保住了 §4 那條
   「伺服器從不下發對手 OK 狀態」的 fairplay 性質 —— 現在它從協定保證
   降級成我們的設計選擇，所以必須有測試把它釘住。
3. **重放原始參數。** 攔到的 `I_am_ok` 呼叫原封不動用原始 emit 送出，
   插件永遠不需要知道它的協定長什麼樣（§4 設計輪廓第 4 點）。

### 沒插件的對手

自動退回第一期行為（3 秒誤按反悔窗口）。不需要偵測、不需要自律 ——
沒有側通道就是什麼都不知道。

### ⬜ 還沒被真實驗證的三件事

前幾輪實測都因為上面那些 bug 沒走到，修完之後還沒有機會重跑：

| 要驗的           | 怎麼看                                 |
| ---------------- | -------------------------------------- |
| 硬底線真的會觸發 | 送出原因是 `arbiter` 而不是 `failsafe` |
| 讀秒沒問題       | 終端機沒有 `✗ 輪詢出錯`                |
| 階段結束會放掉   | 送出原因出現 `phase-ended`             |

前兩項是同一件事的正反面。**只要看到一次 `failsafe`，就代表硬底線又失效了。**

### 規則版本：不相容就退化，不要嘗試相容

雙邊仲裁一旦上線，版本不同的後果**不是顯示錯誤，是勝負**：我方 v1（3 秒底線）
碰上對手 v2（等雙方就緒），我方會在對手還沒好時就送出 —— 又回到「先承諾的人
被懲罰」，正是這個功能要消除的東西。

所以握手時交換版本，**不相容就雙方都退回單邊模式**。單邊模式本來就是安全的
預設，退回去不傷害任何人 —— 這比維護 N×N 相容矩陣誠實得多。

### 自動更新：靜默下載，明確套用

仲裁會改變勝負。**靜默把規則版本換掉，等於在玩家不知情時改變他對戰的行為**，
而且真出問題時「昨天好好的今天壞了」而他完全不知道更新過，排查會非常痛苦。

建議下載靜默、套用要玩家確認（而且不要在對戰中）。

> 附帶：若之後改成雀魂式的 15+15（固定時間 + 儲備時間），跟現在的架構相容
> —— `deadlineSeconds` 換成函式即可，三個不變量都不受影響。但要注意
> **伺服器仍然是 31 秒硬砍**，儲備時間只能在那之內分配，不可能真的延長。
> 文案要講清楚，否則玩家會以為插件能改伺服器判定。

## WP-13：實況轉播

牌譜流的即時傳輸。「登入才能看 or 120 秒延遲」是為了避免變成即時作弊工具。

排最後不只是因為相依：它是四項裡唯一**對外**的，牽涉帳號、頻寬、內容審核，
而且一旦有觀眾就會有人要求「即時」。延遲策略要在協定層強制，不能只是 UI 選項。

## 動手前要先 probe 的四件事

現在雙開成立了，這些都是一場對戰就能問完的。**每一條都會影響 V1 規則能不能照寫**：

1. **移動階段到底有沒有「鎖定按鈕」？** constants.ts 只記了 `OK_BUTTON`
   （`MainA` / 材質 `ok` / (570,630) / `disabledFrame "2"`）。V1 規則 1 說
   「準備按鈕替代鎖定按鈕」「鎖定按鈕已經隱藏」，但 repo 裡沒有第二顆鈕的
   任何記錄。是兩顆鈕，還是「OK = 鎖定」？寫錯的話整條規則 1 要重寫。
2. **「收牌」是什麼事件？** 已知對手側有 `cardclickedB` / `cardrotateB`。
   V1 規則 2 把出牌、收牌、旋轉當三種操作，但出牌與收牌可能共用
   `cardclickedB`，區分不出來的話 A/B 兩種取消策略的語意要改。
3. **狀態效果（麻痺、降低移動、自壞剩一回）叫什麼事件？** V1 規則 3 的觸發
   條件靠它。目前完全沒有狀態效果的模型。
4. **match id 可不可觀測？** `ROOM_EVENTS` 有 `match_room_make` / `joinRoom` /
   `room_in`，但沒實測過裡面有沒有能讓 ulgg 把兩個玩家配起來的穩定 id。
   這是 ulgg 那條路的第一個未知（open-questions §3 也列了同一題）。

## 移動規則 V1 的評論

逐條，只講會改變設計的部分。

### 規則 0：顯示對手的「不良紀錄」—— 建議改成中性統計

這條跟 §4 最後一節「社群立場」直接衝突。那節的結論是：

> 拖條在社群裡**有爭議**，不是共識性的濫用行為。功能定位不是「禁止慢慢想」，
> 而是消除「先按 OK 的人被懲罰」這個不對稱。文案要照這個講，不要寫成抓拖條仔。

而且證據很弱：「15~30 秒才出聖水」會抓到思考、網路延遲、離開座位。
把這些標成「不良紀錄」是拿弱證據下強結論。

**建議**：記錄照做，但顯示成中性事實 ——「本場平均決策 18.4 秒 / 3 次用滿 30 秒」，
不要有「不良」這種判定詞，不要跨場累積成聲望分數，純本機不上傳。
資訊一樣有用，但不會變成騷擾工具。

### 規則 1：需要先確認鎖定按鈕存不存在

見上面 probe 第 1 條。若「OK = 鎖定」是同一顆，那「準備」就是把 OK 攔下來
不送 —— 那正是第一期在做的事，只是窗口從 3 秒變成「直到雙方都好」。

### 規則 2：「操作」的定義比原本寫的細

玩家補充（2026-08-02）：**轉牌要分位置**。

| 動作         | 算不算操作 |
| ------------ | ---------- |
| 在手牌中轉牌 | **不算**   |
| 轉已打出的牌 | **算**     |

**✅ 兩件事都實測解決了**（2026-08-02，細節見
[battle-events.md](battle-events.md)）：

1. **出牌 / 收牌分得出來** —— `cardclickedX(num, 出牌?, ?)`，
   第一個布林 `true` 是出牌、`false` 是收牌。
2. **手牌轉牌 / 場上轉牌**：伺服器**兩種都廣播**，事件本身分不出來，
   但插件自己追蹤「目前在場上的 num 集合」就分得出：

   ```
   cardclickedX(num, true)   → 加入
   cardclickedX(num, false)  → 移出
   cardrotateX(num)  在集合裡 → 場上轉牌（算操作）
                     不在      → 手牌轉牌（不算操作）
   ```

   這是對**不透明 ID** 做狀態追蹤，不需要知道那張牌是什麼 —— 所以對手側
   也能用，而且不碰隱藏資訊（`num` 本身是卡片識別碼，**不得記錄或顯示**）。

所以規則 2 可以照玩家說的完整實作。

### 規則 2（續）：C 型會把不對稱又帶回來

A／B 的差別在我方操作要不要取消自己的準備，語意清楚。

C（無論如何都不取消）等於原本的鎖定行為。問題在**混搭**：我選 C、對手選 A，
我先準備好之後對手可以無限磨我 —— 這就是這整個功能要消除的那個不對稱。
建議 UI 直接標「等同原本的鎖定行為」並寫明代價，而不是跟 A/B 平列成三個
中性選項。

另外「收牌」能不能跟「出牌」區分，見 probe 第 2 條。

### 規則 3：條件可以完整實作（原本的建議已作廢）

> **2026-08-02 更正。** 這一節原本寫「觸發條件需要一個現在完全不存在的狀態
> 效果模型，建議 V1 退化成單一條件」。實測之後不成立 —— 模型一直都在，
> 只是還沒去看。詳見 [battle-events.md](battle-events.md)。

兩個條件都拿得到：

- **手牌有聖水／聖杯** → `event_asset` 的 frame 有 `holy` / `holy_enemy` 兩個

所以規則 3 照原本寫的做就好，不需要退化。

### 規則 4：方向對，但要補一條「送達失敗怎麼辦」

缺的是失敗路徑：如果鎖定訊號沒送到其中一方？**用不變量 1 兜底** ——

還有 ulgg 得先知道兩個玩家在同一場對戰，見 probe 第 4 條。

## 雙開的實際做法（2026-08-02 實證）

[launching.md](launching.md) 附註的「伺服器依 IP 擋多重啟動，兩個客戶端必須
來自不同 IP」**成立，沒有被推翻**。同一份文件開的處方也證實可行：

> 網頁版可以靠瀏覽器的 VPN 擴充功能，桌面版沒有等價做法。

實際跑起來的組合：

| 客戶端 | 出口 IP              | 接法      |
| ------ | -------------------- | --------- |
| 網頁版 | UrbanVPN（瀏覽器內） | CDP :9334 |
| 桌面版 | 本機 IP              | CDP :9333 |

VPN 只掛在網頁版那邊，桌面版走本機，兩邊 IP 不同才過得了多重登入檢查。

**這對 WP-12 是必要條件**：localhost 串兩個插件驗協定，前提是兩個客戶端
真的能同時在線對打。開發環境的設定要連 VPN 這步一起寫進去，否則接手的人
會卡在「禁止多重啟動遊戲」而以為是插件的問題。
